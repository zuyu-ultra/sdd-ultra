# 存量项目兼容与回归红线

对已有代码的功能开发和缺陷修复，项目自身的成熟惯例优先于通用范式。除非既有做法违反宪章、明确安全要求或用户指令，否则不要为了“更现代”“更干净”另起一套结构。

## 两条不可豁免红线

1. **新需求不得破坏老功能。** 受影响范围内的既有可观察行为、公共契约、数据兼容性和已有测试必须保持通过；用户批准、`spec.md` 声明或风险接受都不能豁免。
2. **修复 Bug 不得引入新 Bug。** 修复必须先有可复现失败，再以最小改动修复，并同时验证相邻正常路径、边界路径和原有回归集。

检测到任何回归、未知基线失败、公共契约不兼容或数据不兼容时，立即停止；不得勾选实现任务、不得声称完成、不得用新增补丁掩盖后继续。

如果产品目标确实需要替换既有行为，本 feature 仍必须让当前 `PB-###`、公共契约和既有调用方保持通过，只能采用以下兼容演进方式：

- 在旧入口后增加兼容适配，保持原输入、输出、错误与副作用语义。
- 提供并行的新版本、新端点或新协议，让调用方显式迁移，不把旧入口原地改坏。
- 记录调用方清单、迁移顺序、双轨验证和回滚方式；迁移期间新旧基线都必须通过。
- 只有全部调用方完成迁移、零剩余调用方得到可重复证明、旧入口基线仍通过后，才可另立独立退役 feature。退役不能夹在当前功能或 Bug 修复中，也不能破坏任何尚未迁移的调用方。

“用户批准破坏性变更”不是有效例外；需要的是保持兼容的迁移设计与可验证的独立退役流程。

## Hook 与自定义层完整性

模板、replace override、preset、extension、bundle、workflow 和 hook 只能增加约束，不能删除、改写或降级本文件的规则。对每个实际执行的 before/after hook，必须逐个执行以下协议；多个 hook 不能共用一组前后快照：

1. 在单个 hook 执行前，解析该阶段当前真实产物路径，对所有相关普通文件逐文件计算 SHA-256；目录按其全部文件的相对路径、类型和 SHA-256 建立清单。不存在的预期文件使用 `MISSING` 哨兵记录。
2. 执行 hook 后重新解析路径并重新计算；文件新增、删除、重命名、路径目标变化或摘要变化都属于实质变化。只比较 mtime、文件大小或 Git 状态不合格；本地模式仍不得调用 Git。
3. 无论摘要是否变化，都重新读取阶段关键产物，并完整重跑该阶段适用的 `PB-###`、`NM-###`、调用方、变更前基线和回归矩阵验证，以及 requirements checklist；摘要变化还必须触发下述批准失效处理。
4. Hook 若改变 `spec.md`，规格批准及所有下游批准立即失效；若改变 `plan.md`、research/data model/contracts/quickstart 或其证据，计划和任务批准立即失效；若改变 `tasks.md`，任务批准立即失效。
5. Hook 删除必要章节、引入未经批准的 `NM-###`、漏掉 `PB-###`、改变调用方/公共契约、使基线或矩阵不可验证时立即阻断，回到拥有该产物的阶段。不得继续请求下游批准。

可选 hook 仅被展示而未执行时不会产生文件变化；用户随后选择执行时，也必须在执行当下完成相同的逐 hook 快照和重验。

## 变更前必须取得的证据

在提出实现方案前，按以下顺序只读检查：

1. **同一个类或组件**：现有方法、字段、构造方式、生命周期和相邻测试。
2. **同一个模块或 package**：同类需求的实现、错误处理、日志、依赖注入、数据访问和测试夹具。
3. **同一个项目**：命名、目录、公共接口、配置、格式化、lint、测试命令和架构边界。
4. **既有行为基线**：需求触达的正常、异常、边界和兼容场景，以及这些场景当前对应的测试或可重复验证步骤。

记录最接近的现有实现；有多个候选时记录最相关的至多三个。搜索不到也要记录检索范围和关键词，不能把“没看到”当作“项目里没有”。本地模式使用 `rg`、目录读取、语言工具与测试命令，不得调用 Git。

## 复用优先决策

固定决策顺序为：**直接调用现有实现 > 兼容扩展现有实现 > 提炼共享实现 > 仅凭已批准的 `NM-###` 新增**。不得跳级。

每个计划新增的 method、class、module、endpoint、schema 或 helper 都必须先回答：

- 哪个现有符号或路径最接近？
- 能否直接调用、扩展、参数化或在原方法中增加兼容分支？
- 若不能复用，具体约束是什么？
- 新实现将遵循哪几个同类代码样例的命名、边界、错误处理和测试写法？

存在等价能力时禁止创建重复实现。只有在复用会破坏单一职责、公共契约、性能/安全约束，或根本不存在可扩展点时，才允许新增抽象。每个拟新增的 method/class/module/helper/endpoint/schema/dependency 必须分配稳定的 `NM-###`（New Member）例外编号，在 `plan.md` 记录搜索范围、候选实现、拒绝复用的具体原因、放置位置和将沿用的项目样例，并由用户随计划一起批准。缺少 `NM-###` 或复用证据时，计划关卡失败。

## 规格、计划与任务的强制内容

### `spec.md`

- 用 `PB-###` 标识必须保持的既有行为（Protected Behavior）。
- 明确本次变化与不变化的边界、旧调用方/用户旅程、兼容要求。
- Bug 修复写出复现条件、错误现象、期望行为及相邻不应改变的场景。

### `plan.md`

- **现有实现与惯例证据表**：需求触点、现有符号/路径、同类样例、采用的项目惯例。
- **复用决策表**：直接复用/扩展/新增；新增必须引用 `NM-###`，并含检索证据与拒绝复用理由。
- **影响面表**：调用方、公共接口、数据、配置、并发/性能、安全和运维触点。
- **回归验证矩阵**：每个 `PB-###`、相关 `FR-###`、Bug 复现、相邻场景对应的测试路径、验证命令和预期结果。
- 明确变更预算：预计修改的既有文件和确有必要的新文件；Bug 修复不得夹带无关重构。

### `tasks.md`

- 实现前先运行并记录受影响测试基线；基线失败时停止并区分既有失败与本需求问题。
- 每个代码任务点名复用或扩展的现有符号与准确路径；确需新增时引用已批准的 `NM-###`；不得只写“创建一个新的……”。
- 新功能必须包含所有 `PB-###` 的回归任务。
- Bug 修复必须包含：复现测试先失败、最小修复、相邻场景测试、受影响回归集、项目标准验证。
- 最后一阶段必须重新运行与变更前相同的基线命令，并运行项目定义的 lint/typecheck/build/test；无法运行的必需验证是 blocker，不是可忽略备注。

## 实现关卡

1. 在改代码前读取目标类/模块及相邻测试，确认 `plan.md` 的复用证据仍然成立。
2. 先运行计划中的基线命令并记录退出码。基线未知或失败时停止，不在不可靠基线上改代码。
3. Bug 修复先新增或确认一个能稳定复现问题的测试，并观察它在修复前因目标 Bug 失败。
4. 采用能满足需求的最小改动。不得顺手改名、搬目录、换架构、抽公共层或格式化无关文件。
5. 新增符号前再次搜索等价实现，并核对对应 `NM-###`。发现可复用项，或实现时才发现需要未批准的新符号时立即停止；回到计划修正复用决策，原计划和任务批准失效。
6. 每个逻辑任务完成后运行最窄相关测试；阶段完成后运行受影响测试集；全部完成后运行回归验证矩阵和项目标准验证。
7. 任一旧测试由通过变为失败、`PB-###` 不再满足、Bug 修复测试之外出现新失败，立即停止并保留失败证据。不得标记相关任务完成。

## 完成证据

完成报告必须列出：

- 复用/扩展的现有符号和路径，以及确有必要新增的符号、`NM-###` 与理由。
- 遵循的项目惯例样例。
- 变更前与变更后运行的同一组基线命令、退出码和结果。
- Bug 复现测试的“修复前失败、修复后通过”证据。
- `PB-###` 回归矩阵结果、项目标准 lint/typecheck/build/test 结果。
- 未运行的验证；只要其中有必需项，就把状态报告为 blocked/incomplete，不能报告完成。
