## 用户输入

```text
$ARGUMENTS
```

如果用户输入非空，**必须**在继续之前考虑它。

## 执行前检查

### 本地零 Git 命令策略（最高优先级）

读取 `.specify/task-management.json`。如果 `backend` 为 `local` 或 `vcs` 为 `none`，本阶段不得执行 `git`、检查 `.git`、读取 remote/branch/status/diff/log，且 before/after hooks 中所有 `speckit.git.*` 或会启动 `git` 的钩子一律跳过；此规则覆盖钩子的强制标志。

### Hook 产物完整性协议（所有实际执行的 before/after hook 强制）

- 在执行首个 hook 前先通过 `.specify/feature.json` 或下方步骤 1 的 paths-only 结果解析 `FEATURE_DIR` 和 `FEATURE_SPEC`；如果为此提前执行了步骤 1，后面不得再运行第二次。
- 对**每一个**实际执行的 hook 单独在执行前后建立 SHA-256 快照，至少包含 `.specify/feature.json`、`FEATURE_SPEC`、`FEATURE_DIR/checklists/requirements.md`，以及存在的 `plan.md`、`research.md`、`data-model.md`、`quickstart.md`、`contracts/` 全部普通文件和 `tasks.md`。目录快照同时记录相对路径；缺失文件记录 `MISSING`。不得用 mtime、大小或 Git 状态替代。
- Hook 后重新解析路径并逐文件比较；新增、删除、重命名、解析目标变化或摘要变化都算实质变化。无论摘要是否变化，都重新读取规格并重验全部 `PB-###`、变化/不变边界、旧调用方/公共契约、Bug 复现和 requirements checklist；若已有 plan/tasks，还要重验 `NM-###`、调用方、变更前基线与回归矩阵。
- Hook、replace override、preset 或 extension 不得删除或弱化 `## 存量行为与兼容性`。旧规格缺少该章节时必须补齐。任一重验失败立即阻断，不能进入澄清或完成报告。
- Hook 改变 `spec.md` 或检查表时，规格及全部下游批准立即失效；改变 plan 设计产物时，计划和任务批准失效；改变 `tasks.md` 时任务批准失效。必须报告变化文件和前后 SHA-256，并回到对应阶段重新批准。
- 可选 hook 只展示时不执行快照；用户随后实际执行时必须在当时应用完整协议。

**检查扩展钩子（澄清之前）**：

- 检查项目根目录是否存在 `.specify/extensions.yml`。
- 如果存在，读取它并查找 `hooks.before_clarify` 键下的条目。
- 如果 YAML 无法解析或无效，静默跳过钩子检查并正常继续。
- 过滤掉显式设置 `enabled: false` 的钩子。没有 `enabled` 字段的钩子默认视为启用。
- 对每个剩余钩子，**不要**尝试解释或求值钩子的 `condition` 表达式：
  - 如果钩子没有 `condition` 字段，或其值为 null/空，则视为可执行。
  - 如果钩子定义了非空 `condition`，跳过该钩子，并将条件求值留给 HookExecutor 实现。
- 对每个可执行钩子，根据其 `optional` 标志输出以下内容：
  - **可选钩子**（`optional: true`）：

    ```text
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```

  - **强制钩子**（`optional: false`）：

    ```text
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    Wait for the result of the hook command before proceeding to the Outline.
    ```

    输出上述块后，**必须**实际调用钩子并等待其完成，再继续执行大纲。调用方式与当前
    agent/session 中自行运行该命令的方式相同；实际调用形式可能不同于上面显示的字面
    `{command}` id，例如 skills 模式 agent 使用 `/skill:speckit-...` 或
    `$speckit-...`。只输出块并不等于运行钩子。执行前后必须完成逐 hook SHA-256 快照和
    全量适用重验；产物变化造成的批准失效未处理前不得继续大纲。
- 如果没有注册钩子，或 `.specify/extensions.yml` 不存在，静默跳过。

## 大纲

目标：检测并减少活动功能规格中的歧义或缺失决策点，并将澄清直接记录到规格文件。

注意：此澄清工作流应在调用 `$speckit-plan` **之前**运行并完成。如果用户明确表示跳过
澄清，例如进行探索性 spike，可以继续，但必须警告下游返工风险会增加。

在此 Codex Skill 中，`{SCRIPT}` 保留上游“按运行环境选择先决条件检查器”的占位符语义：

- Bash：`scripts/bash/check-prerequisites.sh --json --paths-only`
- PowerShell：`scripts/powershell/check-prerequisites.ps1 -Json -PathsOnly`
- Python：`scripts/python/check_prerequisites.py --json --paths-only`

这些上游路径相对于 `.specify/`。当前中文离线资产提供 Python 实现，因此 Codex 应从仓库
根目录运行 `python3 .specify/scripts/python/check_prerequisites.py --json --paths-only`。

执行步骤：

1. 从仓库根目录运行 `{SCRIPT}` **一次**，使用组合
   `--json --paths-only` / `-Json -PathsOnly` 模式。解析最小 JSON payload 字段：
   - `FEATURE_DIR`
   - `FEATURE_SPEC`
   - 可选记录 `IMPL_PLAN`、`TASKS`，供未来链式流程使用。
   - 如果 JSON 解析失败，中止并指示用户重新运行 `$speckit-specify`，或验证功能分支环境。
   - 如果参数中有单引号，例如 `I'm Groot`，使用转义语法，例如
     `'I'\''m Groot'`；如果可能，也可使用双引号：`"I'm Groot"`。

2. **如果存在**，加载 `/memory/constitution.md` 中的项目原则和治理约束。已有项目还要根据规格触点只读检查目标类/组件、同模块实现、调用方、公开契约和相邻测试；能从项目证据确定的事实直接记录，不要反问用户，也不要用外部惯例覆盖。

3. 加载当前规格文件。使用以下分类体系执行结构化歧义与覆盖扫描。对每个类别标记状态：
   清晰 / 部分 / 缺失。生成用于确定优先级的内部覆盖图；除非不会提出任何问题，否则
   不要输出原始覆盖图。

   功能范围与行为：

   - 核心用户目标与成功标准。
   - 明确的范围外声明。
   - 用户角色/persona 区分。

   存量行为与兼容边界（已有项目或 Bug 修复为强制类别）：

   - 当前代码、公开接口、测试和文档已经表现出的可观察行为；将未明确改变的行为分配为 `PB-###`。
   - 允许改变与明确不得改变的边界，包括默认值、错误类型/错误码、副作用顺序、数据格式和向后兼容性。
   - 在内部参考目标类、同模块与同项目的现有行为和惯例以避免错误提问；符号级复用候选只供后续计划研究，不写入 `spec.md`。
   - Bug 的准确复现条件、当前错误结果、期望结果，以及修复后必须保持不变的相邻正常场景。

   领域与数据模型：

   - 实体、属性、关系。
   - 身份与唯一性规则。
   - 生命周期/状态转换。
   - 数据量/规模假设。

   交互与 UX 流程：

   - 关键用户旅程/序列。
   - 错误/空/加载状态。
   - 可访问性或本地化说明。

   非功能质量属性：

   - 性能（延迟、吞吐量目标）。
   - 可扩展性（水平/垂直扩展、限制）。
   - 可靠性与可用性（uptime、恢复预期）。
   - 可观测性（日志、指标、追踪信号）。
   - 安全与隐私（authN/Z、数据保护、威胁假设）。
   - 合规/监管约束（如有）。

   集成与外部依赖：

   - 外部服务/API 及其失败模式。
   - 数据导入/导出格式。
   - 协议/版本假设。

   边界情况与失败处理：

   - 负向场景。
   - 限流/节流。
   - 冲突解决，例如并发编辑。

   约束与权衡：

   - 技术约束（语言、存储、托管）。
   - 明确权衡或被拒绝的替代方案。

   术语与一致性：

   - 规范词汇表术语。
   - 避免使用的同义词/已弃用术语。

   完成信号：

   - 验收标准的可测试性。
   - 可度量的 Definition of Done 风格指标。

   其他/占位符：

   - TODO 标记/未解决决策。
   - 未量化的含糊形容词，例如 “robust”“intuitive”。

   对每个状态为“部分”或“缺失”的类别，添加候选问题机会，除非：

   - 澄清不会实质改变实现或验证策略。
   - 该信息更适合延后到规划阶段；在内部记录这一点。

4. 在内部生成按优先级排序的候选澄清问题队列，最多 5 个。**不要**一次性全部输出。
   应用以下约束：

   - 整个 session 总共最多提出 5 个问题。
   - 每个问题必须能用以下任一方式回答：
     - 2–5 个彼此不同、互斥选项中的一个简短多选答案；或
     - 单词/短语答案，并明确限制为“答案不超过 5 个词”。
   - 只包含答案会实质影响架构、数据建模、任务分解、测试设计、UX 行为、运营就绪度或
     合规验证的问题。
   - 平衡类别覆盖：优先覆盖影响最大的未解决类别；如果仍有一个高影响领域未解决，例如
     安全态势，不要转而询问两个低影响问题。
   - 排除已经回答的问题、琐碎样式偏好和规划层执行细节，除非它们阻碍正确性。
   - 优先选择能降低下游返工风险或避免验收测试错位的澄清。
   - 未解决的高影响兼容边界、`PB-###` 或 Bug 复现语义优先于其他类别；它们不得因五题配额、`done` 或 `proceed` 被静默延后。若配额耗尽仍未解决，标记为阻塞并停止进入计划阶段。
   - 如果仍有超过 5 个类别未解决，按 `Impact * Uncertainty` 启发式选择前 5 个。

5. 顺序提问循环（交互式）：

   - 每次**严格只展示一个**问题。
   - **问题写作质量**，适用于每个多选或短答问题：
     - 以 `**问题：**` 开头，后接以 `？` 结尾的完整疑问句。`？` 前的文本必须能独立
       表达完整含义。
     - **绝不**使用主题标签、章节标题或需求 id 作为问题本身。例如
       `Acceptance device/runtime matrix (FR-023)` 是无效的，因为它只是标签而非问题。
     - 问号后唯一允许的后缀是可选的括号需求/问题 id。精确格式为
       `**问题：** <疑问句>？` 或 `**问题：** <疑问句>？ (FR-023)`。不得把 id 放在
       `？` 之前，也不得只用 id（无论是否带主题标签）作为完整 prompt。
     - 紧接问题行之后，在推荐/选项之前，用一句通俗的“为什么重要”说明对验收或发布的
       利害关系。
     - 使用日常措辞；只在同一句中定义后才引入术语。自检：不了解 Spec Kit 的读者仅凭
       Question 行也必须能够回答。可以简短，但不能使用晦涩标签。

   - 对多选问题：
     - **分析所有选项**，并基于以下因素确定**最合适的选项**：
       - 当前目标类、同模块、同项目代码与测试中已经采用的惯例。
       - 项目没有证据时，才参考此类项目的最佳实践和外部相似实现。
       - 降低安全、性能、可维护性风险。
       - 与规格中明确项目目标或约束保持一致。
     - 在顶部突出显示**推荐选项**，并用 1–2 句清楚解释其为何是最佳选择。
     - 格式：`**推荐：** 选项 [X] - <理由>`。
     - 然后把所有选项呈现为 Markdown 表格：

       | 选项 | 描述 |
       |------|------|
       | A | <选项 A 描述> |
       | B | <选项 B 描述> |
       | C | <选项 C 描述>（按需增加 D/E，最多 5 个） |
       | Short | 提供其他短答案（不超过 5 个词）（仅在适合自由形式替代答案时包含） |

     - 表格后添加：“你可以回复选项字母（例如 `A`），回复 `yes` 或 `recommended` 接受
       推荐，也可以提供自己的短答案。”

   - 对没有有意义离散选项的短答问题：
     - 先根据当前项目代码、测试和公开契约，再根据最佳实践与上下文提供**建议答案**。
     - 格式：`**建议：** <建议答案> - <简短理由>`。
     - 然后输出：“格式：短答案（不超过 5 个词）。你可以回复 `yes` 或 `suggested`
       接受建议，也可以提供自己的答案。”

   - 用户回答后：
     - 如果用户回复 `yes`、`recommended` 或 `suggested`，使用先前给出的推荐/建议作为答案。
     - 否则，验证答案能映射到一个选项，或满足不超过 5 个词的限制。
     - 如果有歧义，快速请求消歧；这仍计入同一个问题，不进入下一个问题。
     - 答案满足要求后，将其记录在工作内存中；此时不要写入磁盘，然后移到队列中的下一个
       问题。

   - 在以下任一条件成立时停止继续提问：
     - 所有关键歧义提前解决，剩余队列项不再必要；或
     - 用户发出完成信号：`done`、`good`、`no more`；或
     - 已提出 5 个问题。
   - 绝不提前透露队列中的后续问题。
   - 如果一开始就没有有效问题，立即报告不存在关键歧义。

6. 每个答案被接受后执行集成，采用增量更新方式：

   - 保留只在开始时加载一次的规格内存表示及原始文件内容。
   - 对本 session 中第一个集成答案：
     - 确保存在 `## 澄清记录` 章节；如果缺失，在规格模板中最高层上下文/概览章节之后
       创建。
     - 在该章节下，为当天创建 `### 会话 YYYY-MM-DD` 子标题（如尚不存在）。
   - 接受答案后立即追加一行：`- 问：<question> → 答：<final answer>`。
   - 然后立即把澄清应用到最合适的章节：
     - 功能歧义 → 更新 Functional Requirements 中的项目，或新增一项。
     - 用户交互/actor 区分 → 在 User Stories 或 Actors 子章节（如存在）更新澄清后的
       角色、约束或场景。
     - 数据形状/实体 → 更新 Data Model，添加字段、类型、关系并保留顺序；简洁注明新增约束。
     - 非功能约束 → 在 Success Criteria > Measurable Outcomes 中新增或修改可度量标准，
       将含糊形容词转为指标或明确目标。
     - 边界情况/负向流程 → 在 Edge Cases / Error Handling 下添加项目；如果模板提供了
       对应占位符，则创建该子章节。
     - 存量行为/兼容性 → 更新 `## 存量行为与兼容性`，只补齐调用方可观察的稳定 `PB-###`、允许/禁止改变边界和公共契约；Bug 修复同时写入复现条件和相邻不变场景。不得写入 method/class/helper 等符号级复用候选，它们属于 `research.md`/`plan.md`。旧规格缺少该章节时必须创建。
     - 术语冲突 → 在整个规格中统一规范术语；只有在必要时才保留原术语，并一次性注明
       `(formerly referred to as "X")`。
   - 如果澄清使之前的含糊陈述失效，替换该陈述，而不是重复添加；不得留下过时的矛盾文本。
   - 每次集成后保存规格文件，采用原子覆盖，以尽量降低上下文丢失风险。
   - 保持格式：不重排无关章节；维持标题层级。
   - 每项插入的澄清都应最小化且可测试，避免叙事漂移。

7. 每次写入后及最终阶段都进行验证：

   - 澄清 session 对每个已接受答案恰好包含一个项目，不得重复。
   - 已提出并接受的问题总数不超过 5。
   - 更新后的章节中，不再保留该答案原本要解决的含糊占位符。
   - 不再存在矛盾的旧陈述；扫描并移除现在无效的替代选项。
   - Markdown 结构有效；允许新增的标题只有 `## 澄清记录`、`### 会话 YYYY-MM-DD`，以及旧规格缺失时用于红线补全的 `## 存量行为与兼容性`。
   - 术语一致：所有更新章节使用相同规范术语。

8. 将更新后的规格写回 `FEATURE_SPEC`。

9. **重新验证规格质量检查表**（如果存在）：

   - 检查 `FEATURE_DIR/checklists/requirements.md` 是否存在。
   - 如果不存在，静默跳过本步骤。
   - 如果存在：
     1. 读取检查表文件。
     2. 识别所有 GitHub task-list checkbox 行：匹配 `- [ ]`、`- [x]` 或 `- [X]` 的行；
        大小写不敏感，并允许嵌套项带前导空白。忽略代码围栏内的匹配项。忽略所有其他内容，
        包括标题、备注、非 checkbox 项目和 metadata。
     3. 对每个 checkbox 行，把当前 marker 状态（checked 或 unchecked）及项目文本记录到
        before-snapshot 列表。
     4. 根据**更新后的**规格，即步骤 7 中刚保存的版本，重新评估每个 checkbox 项目。
     5. 仅在 checked/unchecked 状态实际变化时更新 checkbox 项目：
        - 如果项目现在通过且之前未选中，将 `[ ]` 改为 `[x]`。
        - 如果项目现在失败且之前已选中，将 `[x]`/`[X]` 改为 `[ ]`。
        - 如果状态未变化，marker 保持原样；保留现有大小写以避免装饰性 diff。
     6. 保存更新后的检查表文件。**只切换状态已变化 checkbox 行的 `[ ]`/`[x]`
        marker 部分。**所有其他文件内容——标题、metadata、备注、行顺序、空白——必须保持
        不变，以避免噪声 diff。
     7. 比较 before-snapshot 与当前状态，计算供完成报告使用的三个列表：
        - **新通过**：从 unchecked 变为 checked 的项目。
        - **回退**：从 checked 变为 unchecked 的项目。
        - **仍未选中**：保持 unchecked 的项目。
     8. 将前后通过数记录为 checked/total checkbox 项目数，例如
        `12/16 → 15/16 items passing`。

行为规则：

- 如果没有发现有意义的歧义，或所有潜在问题影响都很低，回复：
  “未检测到值得正式澄清的关键歧义。”并建议继续下一阶段。
- 如果规格文件缺失，指示用户先运行 `$speckit-specify`；不得在此创建新规格。
- 已提问题总数绝不能超过 5 个；同一问题的澄清重试不算新问题。
- 除非缺少技术栈会阻碍功能正确性，否则避免推测性技术栈问题。
- 尊重用户提前终止信号：`stop`、`done`、`proceed`；但若仍有高影响兼容边界或 Bug 复现语义未知，只能终止本阶段并报告阻塞，不得建议直接进入计划或实现。
- 如果因为覆盖已完整而没有提问，输出紧凑覆盖摘要，所有类别均为“清晰”，然后建议继续。
- 如果达到配额后仍有未解决的高影响类别，在 Deferred 下明确标记并说明理由。

确定优先级时使用的上下文：`{ARGS}`

## 强制执行后钩子

**向用户报告完成之前，必须完成本章节。**

每个 `after_clarify` hook 执行前后都必须按本文件的“Hook 产物完整性协议”分别快照和比较。
Hook 后无条件重新读取当前规格、检查表和任何既有下游产物，并重验 `PB-###`、调用方、
Bug 复现；若已有计划或任务，同时重验 `NM-###`、变更前基线和回归矩阵。只有全部通过才能
进入完成报告。任何变化按拥有产物的阶段使批准失效，不能用本轮此前的批准继续。

检查项目根目录是否存在 `.specify/extensions.yml`。

- 如果不存在，或 `hooks.after_clarify` 下没有注册钩子，跳到完成报告。
- 如果存在，读取它并查找 `hooks.after_clarify` 键下的条目。
- 如果 YAML 无法解析或无效，静默跳过钩子检查并继续到完成报告。
- 过滤掉显式设置 `enabled: false` 的钩子。没有 `enabled` 字段的钩子默认视为启用。
- 对每个剩余钩子，**不要**尝试解释或求值钩子的 `condition` 表达式：
  - 如果钩子没有 `condition` 字段，或其值为 null/空，则视为可执行。
  - 如果钩子定义了非空 `condition`，跳过该钩子，并将条件求值留给 HookExecutor 实现。
- 对每个可执行钩子，根据其 `optional` 标志输出以下内容：
  - **强制钩子**（`optional: false`）——对每个强制钩子都**必须输出
    `EXECUTE_COMMAND:`**：

    ```text
    ## Extension Hooks

    **Automatic Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}
    ```

    输出上述块后，**必须**实际调用钩子并等待其完成，再继续。调用方式与当前
    agent/session 中自行运行该命令的方式相同；实际调用形式可能不同于上面显示的字面
    `{command}` id，例如 skills 模式 agent 使用 `/skill:speckit-...` 或
    `$speckit-...`。只输出块并不等于运行钩子。调用前后必须完成 SHA-256 快照、重新读取、
    重验和批准失效处理；失败时立即阻断，不得进入完成报告。
  - **可选钩子**（`optional: true`）：

    ```text
    ## Extension Hooks

    **Optional Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```

## 完成报告

- 已提出和已回答的问题数量。
- 更新后的规格路径。
- 被修改的章节名称列表。
- 规格质量检查表状态：如果重新验证了 `FEATURE_DIR/checklists/requirements.md`，显示前后
  通过数，例如 `Spec Quality Checklist: 12/16 → 15/16 items passing`；列出状态发生变化的
  所有项目，包括新选中项（unchecked → checked）和回退项（checked → unchecked）。如果
  仍有未选中项，把它们列为需要注意的领域。
- 覆盖摘要表：列出分类体系中的每个类别及状态——已解决（原为“部分/缺失”且已处理）、
  延后（超过问题配额或更适合规划）、清晰（原本已充分）、仍待处理（仍为“部分/缺失”但
  影响较低）。
- 如果仍有“仍待处理”或“延后”项，建议是继续 `$speckit-plan`，还是在规划后再次运行
  `$speckit-clarify`。
- 建议的下一条命令。
- 只要本次写回使 `spec.md` 发生实质变化，先说明原规格批准已失效，询问：“请审阅澄清后的当前 `spec.md`。是否重新批准此版本进入规划？请回复‘批准规格’，或指出需要修改的内容。”然后停止；不得在同一轮进入 `$speckit-plan`。
