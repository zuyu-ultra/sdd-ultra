# 跨产物一致性分析

## 用户输入

```text
$ARGUMENTS
```

如果用户输入非空，必须在继续之前加以考虑。

## 执行前检查

### 本地零 Git 命令策略（最高优先级）

读取 `.specify/task-management.json`。如果 `backend` 为 `local` 或 `vcs` 为 `none`，本阶段不得执行 `git`、检查 `.git`、读取 remote/branch/status/diff/log，且 before/after hooks 中所有 `speckit.git.*` 或会启动 `git` 的钩子一律跳过；此规则覆盖钩子的强制标志。

**检查分析前的扩展钩子**：

- 在实际执行每个 hook 前，对 `spec.md`、`plan.md`、`tasks.md`、constitution，以及 plan/tasks 点名和独立检索发现的源码、调用方与测试文件分别计算 SHA-256；记录 hook ID、路径与摘要。不得使用 Git。

- 检查项目根目录中是否存在 `.specify/extensions.yml`。
- 如果存在，读取该文件并查找 `hooks.before_analyze` 下的条目。
- 如果 YAML 无法解析或无效，静默跳过钩子检查并照常继续。
- 过滤掉 `enabled` 明确为 `false` 的钩子；没有 `enabled` 字段的钩子默认视为已启用。
- 对每个剩余钩子，不要尝试解释或计算 `condition` 表达式：
  - 如果钩子没有 `condition` 字段，或该字段为 null/空值，则将其视为可执行。
  - 如果钩子定义了非空 `condition`，跳过该钩子，把条件计算留给 `HookExecutor` 实现。
- 对每个可执行钩子，根据其 `optional` 标志输出以下内容。Codex 中调用扩展 skill 时，把规范命令 ID 中的点替换为连字符并添加 `$` 前缀，例如 `speckit.git.commit` 调用为 `$speckit-git-commit`：
  - **可选钩子**（`optional: true`）：

    ```text
    ## 扩展钩子

    **可选前置钩子**：{extension}
    命令 ID：`{command}`
    说明：{description}

    提示：{prompt}
    执行方式：使用与 `{command}` 对应的 Codex `$speckit-*` skill
    ```

  - **强制钩子**（`optional: false`）：

    ```text
    ## 扩展钩子

    **自动前置钩子**：{extension}
    正在执行：`{command}`
    EXECUTE_COMMAND: {command}

    等待钩子命令完成，然后再继续执行“目标”。
    ```

    输出上述区块后，必须实际调用钩子并等待其完成，然后重新计算同一组 SHA-256。采用当前 agent/session 中自己运行该命令时所用的方式；实际调用形式可能不同于上面显示的规范 `{command}` ID，例如 Codex skills 模式使用 `$speckit-*`。仅输出区块并不等于运行钩子。
    - `spec.md` 或 `plan.md` 变化会使上游批准失效：停止分析并返回对应阶段，不能用 post-hook 内容冒充已批准输入。
    - `tasks.md`、constitution、源码或测试变化会使旧分析上下文失效：丢弃已有上下文，从 post-hook 当前状态重新初始化并重新取证；如果同一 hook 再次改变跟踪输入，停止并报告不稳定 hook。
- 上述逐 hook 的 SHA-256、批准/上下文失效、重新取证和不稳定 hook 规则适用于每个**实际执行**的可选或强制钩子；`optional` 只决定是否自动执行。可选钩子一旦被执行，必须等待完成并应用完全相同的前后哈希比较。
- 如果没有注册钩子，或 `.specify/extensions.yml` 不存在，则静默跳过。

## 目标

在实现开始前，识别三个核心产物（`spec.md`、`plan.md`、`tasks.md`）之间的不一致、重复、歧义和定义不足，并审查它们是否以真实项目证据优先复用旧实现、保护既有行为和阻断回归。只有在 `$speckit-tasks` 已成功生成完整 `tasks.md` 后，才能运行此 skill。

## 操作约束

**严格只读**：不得修改任何文件。只输出结构化分析报告。可以提供可选的修复计划，但用户必须明确批准，之后才可由用户手动调用任何会编辑文件的命令。

**宪章权威性**：项目宪章（`.specify/memory/constitution.md`）在本分析范围内**不可协商**。任何宪章冲突自动归为 CRITICAL，并且必须调整 spec、plan 或 tasks；不得削弱、重新解释或静默忽略原则。如果原则本身需要改变，必须在 `$speckit-analyze` 之外，通过一次独立、明确的宪章更新完成。

## 执行步骤

### 1. 初始化分析上下文

从仓库根目录运行一次：

```bash
python3 .specify/scripts/python/check_prerequisites.py --json --require-tasks --include-tasks
```

解析 JSON 中的 `FEATURE_DIR` 和 `AVAILABLE_DOCS`，并派生以下绝对路径：

- `SPEC = FEATURE_DIR/spec.md`
- `PLAN = FEATURE_DIR/plan.md`
- `TASKS = FEATURE_DIR/tasks.md`

如果缺少任一必需文件，立即中止并输出错误消息，同时指导用户运行缺失的前置命令。

对于参数中类似 `I'm Groot` 的单引号，使用转义语法，例如 `'I'\''m Groot'`；也可以尽量改用双引号：`"I'm Groot"`。

### 2. 加载产物（渐进披露）

只从每个产物中加载最低限度的必要上下文。

**从 `spec.md` 加载：**

- 概述/上下文
- 功能需求
- 成功标准（可衡量结果，例如性能、安全、可用性、用户成功和业务影响）
- 用户故事
- 边界情况（若存在）
- `PB-###` 受保护行为、允许/禁止改变边界和 Bug 复现/相邻不变场景

**从 `plan.md` 加载：**

- 架构/技术栈选择
- 数据模型引用
- 阶段
- 技术约束
- 现有符号与调用方、项目惯例、复用决策、`NM-###` 新建例外、影响面、变更预算和回归验证矩阵

**从 `tasks.md` 加载：**

- 任务 ID
- 描述
- 阶段分组
- 并行标记 `[P]`
- 引用的文件路径
- 每项代码任务引用的现有符号或 `NM-###`，以及基线、复现、目标、相邻与完整回归任务

**从宪章加载：**

- 加载 `.specify/memory/constitution.md`，用于原则校验。

**独立核实真实项目证据（必需，不得只相信产物中的声明）：**

- 从 plan/tasks 的每个路径和符号出发，实际打开目标类/函数/组件、同模块文件和相邻测试；路径或符号不存在时记录为 CRITICAL。
- 使用项目内文本/语言符号搜索查找全部可见定义与调用点，再按“目标类/组件 → 同模块/package → 同业务域 → 同项目”寻找至多三个最接近的同类实现。不得用 Git，也不得只搜索计划已经列出的候选。
- 打开项目测试配置、标准 lint/typecheck/build/test 定义和回归矩阵引用的测试文件，核实命令、夹具、断言与 `PB-###`/Bug 场景确实存在。
- 对每项复用或 `NM-###` 决策记录 `artifact-claim -> actual symbol/path -> callers/tests -> verdict`。找不到调用方、测试或项目惯例时必须明确标记证据缺失，不能用计划文字补全。
- 将实际文件的 SHA-256 纳入本次分析身份；报告只对这些精确内容有效。

### 3. 构建语义模型

创建以下内部表示，不要在输出中包含原始产物全文：

- **需求清单**：为每条功能需求（`FR-###`）和成功标准（`SC-###`）记录稳定键。存在显式 `FR-`/`SC-` 标识符时，以它作为主键；也可以另外生成祈使短语 slug 以增强可读性，例如 “User can upload file” → `user-can-upload-file`。只纳入需要构建工作的成功标准，例如负载测试基础设施和安全审计工具；排除上线后的结果指标和业务 KPI，例如“支持工单减少 50%”。
- **用户故事/动作清单**：带验收标准的离散用户动作。
- **任务覆盖映射**：通过关键词或 ID、关键短语等显式引用模式，推断每个任务对应的一个或多个需求/故事。
- **宪章规则集**：提取原则名称和 MUST/SHOULD 规范性陈述。
- **存量保护集**：提取 `PB-###`、公开契约、调用方和允许/禁止改变边界。
- **实现复用映射**：把每项代码任务映射到 plan 中真实的现有符号/路径，或映射到包含完整证据的已批准 `NM-###`。
- **验证映射**：把每个 `PB-###`、`FR-###`、Bug 复现和相邻场景映射到变更前基线、目标测试及变更后同一套回归命令。
- **真实证据映射**：保存独立打开的定义、调用点、相邻实现、测试与配置证据；产物声明和真实代码不一致时以真实项目证据生成发现，而不是静默信任产物。

### 4. 检测轮次（节省 token 的分析）

聚焦高信号发现。总发现数最多 50 条；其余问题聚合进溢出摘要。

#### A. 重复检测

- 识别近似重复的需求。
- 标记质量较低、应合并的表述。

#### B. 歧义检测

- 标记缺少可衡量标准的模糊形容词，例如 fast、scalable、secure、intuitive、robust。
- 标记未解决的占位符，例如 TODO、TKTK、???、`<placeholder>` 等。

#### C. 定义不足

- 需求包含动词但缺少对象或可衡量结果。
- 用户故事缺少与验收标准的对应关系。
- 任务引用了 spec/plan 中未定义的文件或组件。

#### D. 宪章一致性

- 需求或计划元素与 MUST 原则冲突。
- 缺少宪章强制规定的章节或质量关卡。

#### E. 覆盖缺口

- 没有关联任务的需求。
- 无法映射到需求/故事的任务。
- 需要构建工作的成功标准（性能、安全、可用性）没有反映在任务中。

#### F. 不一致

- 术语漂移，即同一概念在不同文件中使用不同名称。
- plan 引用了 spec 中不存在的数据实体，或反之。
- 任务顺序矛盾，例如在没有依赖说明时，集成任务排在基础准备任务之前。
- 互相冲突的需求，例如一处要求 Next.js，另一处指定 Vue。

#### G. 存量复用与回归红线

- 代码任务没有引用可复用/扩展的现有符号与准确路径，也没有引用具备检索证据的 `NM-###`。
- 新建 method/class/module/helper/endpoint/schema/dependency 没有记录候选、拒绝复用理由和沿用的项目样例。
- 使用通用 Model/Service/Endpoint 骨架覆盖当前目标类、同模块或同项目已有结构与惯例。
- `PB-###`、受影响调用方或旧公开契约没有变更前后验证；只测新功能而不测老功能。
- Bug 修复缺少修改前正确失败的复现、最小修复约束、相邻正常/边界测试或完整回归。
- 变更前基线与变更后验证命令不一致、验证环境不可用却仍允许完成，或模板/override/hook 削弱红线。
- plan/tasks 声称的符号、路径、调用方、同类惯例或测试在真实项目中不存在、不是最接近实现，或遗漏搜索发现的等价旧实现。

### 5. 分配严重度

使用以下启发式规则确定优先级：

- **CRITICAL**：违反宪章 MUST、缺少核心规格产物、零覆盖需求阻塞基线功能，或缺少 `PB-###` 回归、Bug 复现、变更前基线、现有符号/`NM-###` 映射。任何会破坏老功能或让 Bug 修复引入新失败的路径均为 CRITICAL。
- **HIGH**：重复或冲突的需求、含糊的安全/性能属性、无法测试的验收标准。
- **MEDIUM**：术语漂移、缺少非功能任务覆盖、定义不足的边界情况。
- **LOW**：风格/措辞改进，以及不影响执行顺序的轻微冗余。

### 6. 生成紧凑的分析报告

输出以下结构的 Markdown 报告，不写入文件：

```markdown
## 规格分析报告

| ID | 类别 | 严重度 | 位置 | 摘要 | 建议 |
|----|------|--------|------|------|------|
| A1 | 重复 | HIGH | spec.md:L120-134 | 两条需求相似…… | 合并表述，保留更清晰的版本 |
```

每项发现一行；生成以类别首字母为前缀的稳定 ID。

**覆盖摘要表：**

```markdown
| 需求键 | 是否有任务？ | 任务 ID | 备注 |
|--------|--------------|---------|------|
```

随后按需输出：

- **宪章一致性问题**（若有）
- **未映射任务**（若有）
- **指标**：
  - 需求总数
  - 任务总数
  - 覆盖率（具有至少一个任务的需求占比）
  - 歧义数量
  - 重复数量
  - CRITICAL 问题数量

### 7. 提供下一步行动

在报告末尾输出简洁的“下一步行动”区块：

- 如果存在 CRITICAL 问题：明确判定实现关卡失败，禁止运行 `$speckit-implement`；指出应返回 `$speckit-specify`、`$speckit-plan` 或 `$speckit-tasks` 的具体位置，并要求修订后重新分析、重新批准任务。

- 给出明确的命令建议，例如“运行 `$speckit-specify` 完善需求”、“运行 `$speckit-plan` 调整架构”、“手动编辑 `tasks.md`，为 `performance-metrics` 增加覆盖任务”。

### 8. 提供修复建议

询问用户：“是否需要我针对优先级最高的 N 个问题提出具体修复编辑建议？”不得自动应用这些编辑。

## 操作原则

### 上下文效率

- **最少的高信号 token**：聚焦可行动的发现，不写穷尽式文档。
- **渐进披露**：逐步加载产物，不要把全部内容倾倒进分析上下文。
- **节省 token 的输出**：发现表最多 50 行，其余汇总。
- **确定性结果**：在文件未变化的情况下重复运行，应产生一致的 ID 和计数。

### 分析准则

- **绝不修改文件**，本阶段是只读分析。
- **绝不臆造缺失章节**；如果不存在，就准确报告。
- **优先处理宪章违规**，这些问题始终为 CRITICAL。
- **兼容红线不可协商**：缺少复用证据、未经批准的新符号、缺失 `PB-###`/Bug 回归或验证不可运行时始终为 CRITICAL；不能因用户简单要求 continue、模板覆盖或 hook 而降级。
- **报告不可跨版本复用**：产物、源码、调用方、测试、配置或 constitution 的任一 SHA-256 变化都会使报告失效；重验完成前 CRITICAL 关卡保持阻塞。
- **使用具体实例而不是穷尽规则**，引用实际位置，不写泛泛模式。
- **优雅报告零问题**，输出成功报告和覆盖统计。
