# 需求质量检查表

## 脚本映射

根据项目安装的脚本类型选择对应脚本；本中文版 Skill 默认优先使用 Python：

```text
sh: scripts/bash/check-prerequisites.sh --json --template checklist-template
ps: scripts/powershell/check-prerequisites.ps1 -Json -Template checklist-template
py: scripts/python/check_prerequisites.py --json --template checklist-template
```

## 检查表用途：“自然语言需求的单元测试”

**关键概念**：检查表是**需求写作的单元测试**——它验证给定领域中需求的质量、清晰度和完整性。

**不用于验证/测试实现**：

- ❌ 不是“验证按钮能否正确点击”。
- ❌ 不是“测试错误处理是否工作”。
- ❌ 不是“确认 API 返回 200”。
- ❌ 不是检查代码/实现是否符合规格。

**用于验证需求质量**：

- ✅ “是否为所有卡片类型定义了视觉层次要求？”（完整性）
- ✅ “‘突出显示’是否通过具体尺寸/位置进行量化？”（清晰度）
- ✅ “所有交互元素的 hover 状态要求是否一致？”（一致性）
- ✅ “是否定义了键盘导航的可访问性要求？”（覆盖范围）
- ✅ “规格是否定义了 logo 图片加载失败时的处理方式？”（边界情况）

**比喻**：如果你的规格是用自然语言编写的代码，那么检查表就是它的单元测试套件。你测试的是需求是否写得清楚、完整、无歧义并且可供实施——**不是**测试实现是否工作。

**归属与 checkbox 生命周期**：

- 本命令生成的自定义检查表，是由审阅者拥有的需求质量审阅产物。
- `[x]` 表示审阅者认定该需求质量准则已满足。
- `[x]` **不**表示实施工作已完成。
- 本命令负责生成或追加检查项；**不得**把新生成的条目标为 `[x]`。
- 只有审阅者明确提出要求时，agent 才可以协助评估条目。
- `checklists/requirements.md` 是另一份内置规格质量检查表，由 `$speckit-specify` 和 `$speckit-clarify` 维护；不要把这一例外套用到本命令生成的自定义检查表。

## 用户输入

```text
$ARGUMENTS
```

继续之前，**必须**考虑非空的用户输入。

## 执行前检查

### 本地零 Git 命令策略（最高优先级）

读取 `.specify/task-management.json`。如果 `backend` 为 `local` 或 `vcs` 为 `none`，本阶段不得执行 `git`、检查 `.git`、读取 remote/branch/status/diff/log，且 before/after hooks 中所有 `speckit.git.*` 或会启动 `git` 的钩子一律跳过；此规则覆盖钩子的强制标志。

**检查扩展钩子（生成检查表前）**：

- 检查项目根目录是否存在 `.specify/extensions.yml`。
- 如果存在，读取该文件并查找 `hooks.before_checklist` 键下的条目。
- 如果 YAML 无法解析或无效，静默跳过钩子检查并按正常流程继续。
- 过滤掉 `enabled` 被明确设为 `false` 的钩子。没有 `enabled` 字段的钩子默认视为已启用。
- 对每个剩余钩子，**不要**尝试解释或求值钩子的 `condition` 表达式：
  - 如果钩子没有 `condition` 字段，或该字段为 null/空值，则将钩子视为可执行。
  - 如果钩子定义了非空 `condition`，则跳过该钩子，把条件求值留给 HookExecutor 实现。
- 对每个可执行钩子，根据其 `optional` 标志输出以下内容。执行已注册的 Codex Skill 时，把规范命令 ID 中的点号转换为连字符，例如 `speckit.foo` 以 `$speckit-foo` 调用：
  - **可选钩子**（`optional: true`）：
    ```text
    ## 扩展钩子

    **可选前置钩子**：{extension}
    命令：`$speckit-...`（由 {command} 转换）
    描述：{description}

    提示：{prompt}
    如需执行：`$speckit-...`（由 {command} 转换）
    ```
  - **强制钩子**（`optional: false`）：
    ```text
    ## 扩展钩子

    **自动前置钩子**：{extension}
    正在执行：`$speckit-...`（由 {command} 转换）
    EXECUTE_COMMAND: {command}

    等待钩子命令返回结果，然后再继续执行“执行步骤”。
    ```
    输出上述区块后，**必须**在当前 agent/session 中以自己执行命令时相同的方式实际调用该钩子，并等待其完成，然后才能继续。实际调用形式可能不同于上面显示的规范 `{command}` ID；在 Codex skills 模式下使用 `$speckit-...`。仅输出区块并不会运行钩子。
- 如果没有注册钩子，或 `.specify/extensions.yml` 不存在，则静默跳过。

## 执行步骤

1. **设置**：从仓库根目录运行 `{SCRIPT}`，解析 JSON 中的 `FEATURE_DIR`、`AVAILABLE_DOCS` 列表和 `TEMPLATE_CONTENT`。
   - 所有文件路径都必须是绝对路径。
   - 对于参数中类似 "I'm Groot" 的单引号，使用转义语法，例如 `'I'\''m Groot'`；如有可能，也可使用双引号：`"I'm Groot"`。

2. **如果存在**：加载 `/memory/constitution.md`，获取项目原则和治理约束。

2a. **如果存在**：加载 `FEATURE_DIR/discovery.md`，获取 `DD-###` 决策台账。生成检查表时：

   - 不得把已由 `DD-###` 决定的问题重新写成待确认条目；那是已经关闭的决策，不是需求质量缺陷。
   - 标记为“由 Agent 代选”或“延后决策”的条目**应当**优先成为检查条目，让审阅者复核这些用户没有亲自拍板的选择。
   - 规格与某个 `DD-###` 矛盾时，写成明确指向该 `DD-###` 的检查条目，而不是含糊的“需求不清晰”。

3. **澄清意图（动态）**：推导最多**三个**初始的上下文澄清问题，不使用预制问题目录。这些问题**必须**：
   - 从用户措辞和从 spec/plan/tasks 中提取的信号生成。
   - 只询问会实质改变检查表内容的信息。
   - 如果 `$ARGUMENTS` 已经明确给出答案，则逐项跳过相应问题。
   - 精确性优先于覆盖面。

   生成算法：

   1. 提取信号：功能领域关键词（例如 auth、latency、UX、API）、风险指示词（“critical”“must”“compliance”）、利益相关者提示（“QA”“review”“security team”）以及明确产物（“a11y”“rollback”“contracts”）。
   2. 把信号聚类为候选关注领域，最多 4 个，并按相关性排序。
   3. 如果没有明确说明，识别可能的受众和使用时点（author、reviewer、QA、release）。
   4. 检测缺失维度：范围广度、深度/严格度、风险重点、排除边界、可衡量的验收标准。
   5. 从以下问题原型中选择并组织问题：
      - 范围细化，例如：“应当包括与 X 和 Y 的集成接触点，还是只关注本地模块正确性？”
      - 风险优先级，例如：“这些潜在风险领域中，哪些应设置为强制关卡检查？”
      - 深度校准，例如：“这是轻量的提交前 sanity list，还是正式的 release gate？”
      - 受众定位，例如：“这份表只供作者使用，还是由同事在 PR review 中使用？”
      - 边界排除，例如：“本轮是否应明确排除性能调优条目？”
      - 场景类别缺口，例如：“未发现恢复流程——rollback/partial failure 路径是否在范围内？”

   问题格式规则：

   - 如果提供选项，生成一个紧凑表格，列为：`选项 | 候选项 | 重要性`。
   - 选项最多 A–E；如果自由回答更清晰，则省略表格。
   - 绝不要求用户复述已经说过的内容。
   - 避免猜测性分类，不要臆造。如果不确定，明确询问：“请确认 X 是否属于本次范围。”

   无法交互时采用以下默认值：

   - 深度：Standard。
   - 受众：与代码相关时为 Reviewer，否则为 Author；本地模式不假设存在 PR 或版本控制。
   - 关注点：相关性最高的两个聚类。

   输出问题并标记为 Q1/Q2/Q3。收到回答后，如果仍有至少两个场景类别（Alternate/Exception/Recovery/Non-Functional domain）不明确，**可以**再问最多两个有针对性的追问 Q4/Q5，每个问题附一行理由，例如“恢复路径风险仍未解决”。总问题数不得超过五个。如果用户明确拒绝更多问题，则不要升级追问。

4. **理解用户请求**：组合 `$ARGUMENTS` 和澄清答案：
   - 推导检查表主题，例如 security、review、deploy、ux。
   - 汇总用户提到的明确必查项。
   - 把关注点选择映射到分类骨架。
   - 从 spec/plan/tasks 推断缺失上下文，但**不要臆造**。

5. **加载功能上下文**：从 `FEATURE_DIR` 读取：
   - `spec.md`：功能需求和范围。
   - `plan.md`（如果存在）：技术细节、依赖。
   - `tasks.md`（如果存在）：实施任务。
   - 已有项目或 Bug 修复还必须加载：`PB-###`、允许/禁止改变边界、现有符号/调用方、项目惯例、复用决策、`NM-###`、Bug 的 `BUG-###`/`RC-###`、事实时间线、复现证据、因果链、根因状态/置信度、影响范围、检测缺口与回归验证矩阵。用户选择其他关注点也不能排除这一强制类别。

   **上下文加载策略**：

   - 只加载与当前关注领域相关的必要部分，避免倾倒整个文件。
   - 优先把长章节概括成简洁的场景/需求要点。
   - 使用渐进式披露：只有发现缺口时才继续检索更多内容。
   - 如果源文档很大，生成中间摘要项，不要嵌入原始全文。

6. **生成检查表**——使用 `TEMPLATE_CONTENT` 作为结构模板，创建“需求的单元测试”：
   - 如果 `FEATURE_DIR/checklists/` 目录不存在，则创建它。
   - 生成唯一的检查表文件名：
     - 根据领域使用简短、描述性的名称，例如 `ux.md`、`api.md`、`security.md`。
     - 格式：`[domain].md`。
   - 文件处理行为：
     - 如果文件**不存在**：创建新文件，条目从 CHK001 开始编号。
     - 如果文件已存在：向现有文件追加新条目，并从最后一个 CHK ID 继续，例如最后一项为 CHK015，则新条目从 CHK016 开始。
   - 绝不删除或替换已有检查表内容——始终保留并追加。
   - 所有新生成条目都保持未勾选状态（`[ ]`）；checkbox 状态归审阅者所有。
   - 已有项目的兼容审阅使用或追加 `compatibility.md`。模板、replace override、preset、extension 或 hook 缺少此类别时仍必须生成；它们不得削弱兼容红线。

   **核心原则——测试需求，而不是实现**：

   每个检查项都**必须**从以下方面评估**需求本身**：

   - **完整性（Completeness）**：所有必要需求是否都存在？
   - **清晰度（Clarity）**：需求是否明确、具体、无歧义？
   - **一致性（Consistency）**：需求之间是否彼此一致？
   - **可衡量性（Measurability）**：需求是否可以客观验证？
   - **覆盖范围（Coverage）**：所有场景/边界情况是否都已覆盖？

   **分类结构**——按需求质量维度组织条目：

   - **需求完整性**：所有必要需求是否已记录？
   - **需求清晰度**：需求是否具体且无歧义？
   - **需求一致性**：需求是否彼此一致、不冲突？
   - **验收标准质量**：成功标准是否可衡量？
   - **场景覆盖**：所有流程/情况是否已覆盖？
   - **边界情况覆盖**：是否定义了边界条件？
   - **非功能需求**：性能、安全、可访问性等是否已规定？
   - **依赖与假设**：是否已记录并验证？
   - **歧义与冲突**：哪些内容需要澄清？
   - **存量兼容与回归（已有项目必含）**：是否完整定义每个受影响 `PB-###`、允许/禁止改变边界、同类实现与项目惯例证据、复用顺序、所有 `NM-###` 的候选/拒绝理由、Bug 的 `BUG-###`/`RC-###`、事实时间线、复现证据、完整因果链、根因状态/置信度/证伪方式、影响、检测缺口与相邻场景，以及变更前后同一套验证命令？

   **如何编写检查项——“自然语言需求的单元测试”**：

   ❌ **错误**（测试实现）：

   - “验证落地页显示 3 个 episode card。”
   - “测试 hover 状态在桌面端正常工作。”
   - “确认点击 logo 会导航到首页。”

   ✅ **正确**（测试需求质量）：

   - “是否明确规定了 featured episode 的确切数量和布局？”[完整性]
   - “‘突出显示’是否通过具体尺寸/位置进行了量化？”[清晰度]
   - “所有交互元素的 hover 状态要求是否一致？”[一致性]
   - “是否为所有交互式 UI 定义了键盘导航要求？”[覆盖范围]
   - “是否规定了 logo 图片加载失败时的回退行为？”[边界情况]
   - “是否定义了异步 episode 数据的 loading 状态？”[完整性]
   - “规格是否定义了彼此竞争的 UI 元素之间的视觉层次？”[清晰度]

   **条目结构**：

   每个条目应遵循以下模式：

   - 使用问句，询问需求质量。
   - 聚焦规格/计划中**写了什么**或**没有写什么**。
   - 在方括号中包含质量维度，例如 `[Completeness/Clarity/Consistency/etc.]`。
   - 检查已有需求时引用规格章节 `[Spec §X.Y]`。
   - 检查缺失需求时使用 `[Gap]` 标记。

   **按质量维度分类的示例**：

   完整性：

   - “是否为所有 API 失败模式定义了错误处理要求？[Gap]”
   - “是否为所有交互元素规定了可访问性要求？[Completeness]”
   - “是否为响应式布局定义了移动端 breakpoint 要求？[Gap]”

   清晰度：

   - “‘快速加载’是否通过具体时间阈值进行了量化？[Clarity, Spec §NFR-2]”
   - “是否明确定义了‘related episodes’的选择标准？[Clarity, Spec §FR-5]”
   - “‘突出’是否通过可衡量的视觉属性进行定义？[Ambiguity, Spec §FR-4]”

   一致性：

   - “所有页面的导航要求是否一致？[Consistency, Spec §FR-10]”
   - “落地页和详情页之间的 card component 要求是否一致？[Consistency]”

   覆盖范围：

   - “是否为零状态场景（没有 episode）定义了需求？[Coverage, Edge Case]”
   - “是否涵盖并发用户交互场景？[Coverage, Gap]”
   - “是否规定了部分数据加载失败的要求？[Coverage, Exception Flow]”
   - “是否为每个未明确改变的旧行为分配了 `PB-###` 并规定变更前后验证？[Completeness, Compatibility]”
   - “每个拟新增符号是否都有 `NM-###`、检索过的旧实现候选和不能复用的具体理由？[Traceability, Reuse]”
   - “Bug 需求是否规定了修改前正确失败的复现、最小允许改动和必须保持正常的相邻路径？[Measurability, Regression]”
   - “Bug 规格是否证明了从触发条件到第一个错误状态再到外部症状的完整因果链，而不是只记录最终报错？[Completeness, Root Cause]”
   - “每个 `RC-###` 是否记录支持证据、反证/替代假设、置信度和证伪方式，并在未确认时阻断规划？[Traceability, Gate]”
   - “是否说明既有测试、校验或监控为何没有更早发现该 Bug，并形成明确的检测缺口要求？[Coverage, Detection Gap]”

   可衡量性：

   - “视觉层次需求是否可衡量/可测试？[Acceptance Criteria, Spec §FR-1]”
   - “‘平衡的视觉权重’是否可以客观验证？[Measurability, Spec §FR-2]”

   **场景分类与覆盖**（聚焦需求质量）：

   - 检查是否存在以下场景的需求：Primary、Alternate、Exception/Error、Recovery、Non-Functional。
   - 对每类场景询问：“[场景类型]需求是否完整、清晰且一致？”
   - 如果某类场景缺失，询问：“[场景类型]需求是有意排除，还是遗漏？[Gap]”
   - 发生状态变更时包含 resilience/rollback，例如：“是否定义了 migration 失败时的 rollback 要求？[Gap]”

   **可追踪性要求**：

   - 最低要求：至少 80% 的条目**必须**包含至少一个可追踪性引用。
   - 每个条目应引用规格章节 `[Spec §X.Y]`，或使用标记 `[Gap]`、`[Ambiguity]`、`[Conflict]`、`[Assumption]`。
   - 如果没有 ID 系统，则加入：“是否建立了需求和验收标准 ID 体系？[Traceability]”

   **暴露并解决问题**（需求质量问题）：

   围绕需求本身提问：

   - 歧义：“术语‘快速’是否通过具体指标量化？[Ambiguity, Spec §NFR-1]”
   - 冲突：“§FR-10 与 §FR-10a 之间的导航要求是否冲突？[Conflict]”
   - 假设：“‘podcast API 始终可用’这一假设是否经过验证？[Assumption]”
   - 依赖：“是否记录了外部 podcast API 需求？[Dependency, Gap]”
   - 缺失定义：“是否使用可衡量标准定义了‘视觉层次’？[Gap]”

   **内容合并**：

   - 软上限：如果原始候选条目超过 40 个，则按风险/影响确定优先级。
   - 合并检查同一需求方面的近似重复项。
   - 如果低影响边界情况超过 5 个，则合并为一项：“需求是否涵盖边界情况 X、Y、Z？[Coverage]”

   **🚫 绝对禁止**——以下内容会使检查项变成实现测试，而不是需求测试：

   - ❌ 任何以“验证”“测试”“确认”“检查”加实现行为开头的条目。
   - ❌ 引用代码执行、用户操作、系统行为。
   - ❌ “正确显示”“正常工作”“按预期运行”。
   - ❌ “点击”“导航”“渲染”“加载”“执行”。
   - ❌ 测试用例、测试计划、QA procedure。
   - ❌ 实现细节（framework、API、algorithm）。

   **✅ 必需模式**——这些模式测试需求质量：

   - ✅ “是否为[场景]定义/规定/记录了[需求类型]？”
   - ✅ “[模糊术语]是否通过具体标准量化/澄清？”
   - ✅ “[章节 A]和[章节 B]之间的需求是否一致？”
   - ✅ “[需求]是否可以客观衡量/验证？”
   - ✅ “需求是否涵盖[边界情况/场景]？”
   - ✅ “规格是否定义了[缺失方面]？”

7. **结构参考**：按照 `templates/checklist-template.md` 中的规范模板生成检查表，包括标题、meta 部分、分类标题、归属说明、notes 部分和 ID 格式。如果模板不可用，则使用：H1 标题；purpose/created meta 行；一条归属说明，解释 `[x]` 表示审阅者认可需求质量；由 `##` 分类章节组成，每个章节包含 `- [ ] CHK### <requirement item>` 行，ID 从 CHK001 开始全局递增；notes 说明 `$speckit-implement` 会读取检查表状态，但不会修改标记。

8. **报告**：输出检查表文件的完整路径和条目数，并说明本次运行是新建文件还是追加到现有文件。摘要包括：
   - 选择的关注领域。
   - 深度级别。
   - 使用者/时点。
   - 已纳入的用户明确指定必查项。

**重要**：每次调用 `$speckit-checklist` 都使用简短、描述性的检查表文件名，并且新建文件或追加到现有文件。这样可以：

- 创建多种不同类型的检查表，例如 `ux.md`、`test.md`、`security.md`。
- 使用简单、易记的文件名表达检查表用途。
- 在 `checklists/` 文件夹中轻松识别和导航。

为避免混乱，应使用描述性的类型名称，并在不再需要时清理过时的检查表。

## 检查表类型示例与示例条目

**UX 需求质量：** `ux.md`

示例条目（测试需求，而**不是**实现）：

- “视觉层次需求是否使用可衡量的标准定义？[Clarity, Spec §FR-1]”

- “交互状态需求（hover、focus、active）是否定义一致？[Consistency]”
- “是否为所有交互元素规定了可访问性要求？[Coverage, Gap]”

## 反例：绝对不要这样做

**❌ 错误——这些条目测试实现，而不是需求：**

```markdown
- [ ] CHK001 - 验证落地页显示 3 个 episode card [Spec §FR-001]
- [ ] CHK002 - 测试 hover 状态在桌面端正常工作 [Spec §FR-003]
- [ ] CHK003 - 确认点击 logo 导航到首页 [Spec §FR-010]
- [ ] CHK004 - 检查 related episodes 区域显示 3–5 个条目 [Spec §FR-005]
```

**✅ 正确——这些条目测试需求质量：**

```markdown
- [ ] CHK001 - 是否明确规定了 featured episode 的数量和布局？[Completeness, Spec §FR-001]
- [ ] CHK002 - 所有交互元素的 hover 状态要求是否定义一致？[Consistency, Spec §FR-003]
- [ ] CHK003 - 是否清晰定义了所有可点击品牌元素的导航要求？[Clarity, Spec §FR-010]
- [ ] CHK004 - 是否记录了 related episode 的选择标准？[Gap, Spec §FR-005]
- [ ] CHK005 - 是否定义了异步 episode 数据的 loading 状态要求？[Gap]
- [ ] CHK006 - “视觉层次”要求是否可以客观衡量？[Measurability, Spec §FR-001]
```

**关键区别**：

- 错误：测试系统是否正确工作。
- 正确：测试需求是否正确书写。
- 错误：验证行为。
- 正确：验证需求质量。
- 错误：“它是否执行 X？”
- 正确：“X 是否已清晰规定？”

## 执行后检查

**检查扩展钩子（生成检查表后）**：

检查项目根目录是否存在 `.specify/extensions.yml`。

- 如果存在，读取该文件并查找 `hooks.after_checklist` 键下的条目。
- 如果 YAML 无法解析或无效，静默跳过钩子检查并按正常流程继续。
- 过滤掉 `enabled` 被明确设为 `false` 的钩子。没有 `enabled` 字段的钩子默认视为已启用。
- 对每个剩余钩子，**不要**尝试解释或求值钩子的 `condition` 表达式：
  - 如果钩子没有 `condition` 字段，或该字段为 null/空值，则将钩子视为可执行。
  - 如果钩子定义了非空 `condition`，则跳过该钩子，把条件求值留给 HookExecutor 实现。
- 对每个可执行钩子，根据其 `optional` 标志输出以下内容：
  - **可选钩子**（`optional: true`）：
    ```text
    ## 扩展钩子

    **可选钩子**：{extension}
    命令：`$speckit-...`（由 {command} 转换）
    描述：{description}

    提示：{prompt}
    如需执行：`$speckit-...`（由 {command} 转换）
    ```
  - **强制钩子**（`optional: false`）：
    ```text
    ## 扩展钩子

    **自动钩子**：{extension}
    正在执行：`$speckit-...`（由 {command} 转换）
    EXECUTE_COMMAND: {command}
    ```
    输出上述区块后，**必须**在当前 agent/session 中以自己执行命令时相同的方式实际调用该钩子，并等待其完成，然后才能继续。实际调用形式可能不同于上面显示的规范 `{command}` ID；在 Codex skills 模式下使用 `$speckit-...`。仅输出区块并不会运行钩子。
- 如果没有注册钩子，或 `.specify/extensions.yml` 不存在，则静默跳过。
