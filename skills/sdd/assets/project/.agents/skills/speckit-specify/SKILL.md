## 用户输入

```text
$ARGUMENTS
```

如果用户输入非空，**必须**在继续之前考虑它。

## 执行前检查

### 本地零 Git 命令策略（最高优先级）

读取 `.specify/task-management.json`。如果已选择 `local` 或 `vcs` 为 `none`，本阶段不得执行 `git`、检查 `.git`、读取 remote/branch/status/diff/log，且 before/after hooks 中所有 `speckit.git.*` 或会启动 `git` 的钩子一律跳过；此规则覆盖钩子的强制标志。

### 任务管理后端选择（阻塞关卡）

- 在写入任何功能文件前，检查用户是否已为本轮 feature 明确选择 `local` 或 `gitlab`。
- 如果没有明确选择，询问：“本功能的任务使用本地 `tasks.md` 管理，还是同步到 GitLab Issues 管理？”然后**停止并等待用户回复**；不得从 Git remote 推断。
- `local`：`tasks.md` 是任务管理入口，不创建外部 Issues；把选择写为 `{"backend":"local","vcs":"none"}`。这是严格零 Git 命令模式：不得执行 `git`、检查 `.git`、读取 remote、创建或切换分支、调用 `speckit.git.*` 钩子，或用 Git 状态定位 feature。
- `gitlab`：要求精确 GitLab 项目 URL 或 `group/project`。把不含凭据的选择写入 `.specify/task-management.json`；此时只记录目标，不创建 Issue。
- 每个新 feature 都要向用户复述选择。用户可变更后端，但切换到 GitLab 仍需在 `tasks.md` 获批后单独授权外部写入。

### SDD 产物存储选择

- 存储选择与任务管理后端相互独立。解析顺序为：用户本轮指定的需求目录或根目录 > `.specify/sdd-storage.json` > 项目内默认 `specs/`。
- 用户未指定且没有保存配置时直接采用项目内默认，不为默认值额外提问。用户要求 Obsidian 或自定义目录但尚无精确路径时，必须询问一个绝对、已存在的目录并停止；禁止猜测 Obsidian vault。
- `project` 模式使用 `specs/<NNN-short-name>/`。`external` 模式使用获准根目录下的 `YYYY年MM月DD日-中文需求名/`，同名冲突加 `-02`、`-03`；每个需求必须是独立文件夹。
- 外置模式下，需求共创记录、规格、计划、研究、数据模型、契约、quickstart、任务与检查表全部保存在该需求目录。项目里只写 `.specify/feature.json` 和 `.specify/sdd-storage.json` 指针/配置，不创建 `specs/` 副本。
- 恢复已有需求时优先使用用户给出的精确目录，否则使用活动指针；有多个候选时询问用户，禁止按修改时间或“最新”目录猜测。读取前校验路径位于配置的外置根目录内，并校验 `.sdd-feature.json` 的项目归属。

### Hook 产物完整性协议（所有实际执行的 before/after hook 强制）

- 在**每一个** hook 执行前单独建立快照，不得让多个 hook 共用一组快照。快照至少包含 `.specify/feature.json`、`.specify/task-management.json`，以及当前 feature 可解析时的 `discovery.md`、`spec.md`、`checklists/requirements.md`、`plan.md`、`research.md`、`data-model.md`、`quickstart.md`、`contracts/` 全部普通文件和 `tasks.md`。逐个普通文件记录绝对解析路径与 SHA-256；目录同时记录相对路径，不存在的预期文件记录为 `MISSING`。不得用 mtime、大小或 Git 状态代替。
- Hook 完成后重新解析 feature 路径并重新计算同一集合；新增、删除、重命名、解析目标变化或 SHA-256 变化都算实质变化。可选 hook 仅展示时无需快照，但用户随后实际执行时必须在执行当下使用本协议。
- 每个 hook 后无论摘要是否变化，都重新读取存在的规格、检查表和下游产物，完整重跑 `PB-###` 唯一性与覆盖、变化/不变边界、旧调用方/公共契约、Bug 的 `BUG-###`/`RC-###`、根因状态、因果链、复现证据、检测缺口与相邻场景，以及 requirements checklist；若已有 plan/tasks，还要重验复用决策、`NM-###`、调用方、变更前基线和回归矩阵。缺失、冲突或不可验证立即阻断，不能进入大纲或完成报告。
- Hook 不得删除或弱化 `## 存量行为与兼容性`，也不得以 replace override、preset、extension 或自定义模板移除红线内容；活动模板缺少该章节时，本阶段必须主动补齐，而不是照缺失模板输出。
- Hook 造成 `spec.md` 或其验证证据发生实质变化时，已有规格批准及所有下游批准立即失效。报告变化文件和前后 SHA-256，并在继续规划前要求用户重新批准当前规格。

**检查扩展钩子（规格编写之前）**：

- 检查项目根目录是否存在 `.specify/extensions.yml`。
- 如果存在，读取它并查找 `hooks.before_specify` 键下的条目。
- 如果 YAML 无法解析或无效，静默跳过钩子检查并正常继续。
- 过滤掉显式设置 `enabled: false` 的钩子。没有 `enabled` 字段的钩子默认视为启用。
- 如果任务后端是 `local`，再过滤所有 extension 为 `git`、命令 ID 以 `speckit.git.` 开头或实际执行会启动 `git` 的钩子。即使这类钩子标为强制也不得执行；报告“已按本地零 Git 策略跳过”，然后继续纯文件流程。
- 对每个剩余钩子，**不要**尝试解释或求值钩子的 `condition` 表达式：
  - 如果钩子没有 `condition` 字段，或其值为 null/空，则视为可执行。
  - 如果钩子定义了非空 `condition`，跳过该钩子，并将条件求值留给 HookExecutor 实现。
- 对每个可执行钩子，根据其 `optional` 标志输出以下内容：
  - **可选钩子**（`optional: true`）：

    ```text
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```

  - **强制钩子**（`optional: false`）：

    ```text
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    Wait for the result of the hook command before proceeding to the Outline.
    ```

    输出上述块后，**必须**实际调用钩子并等待其完成，再继续执行大纲。调用方式与当前
    agent/session 中自行运行该命令的方式相同；实际调用形式可能不同于上面显示的字面
    `{command}` id，例如 skills 模式 agent 使用 `/skill:speckit-...` 或
    `$speckit-...`。只输出块并不等于运行钩子。执行前后必须完成“Hook 产物完整性协议”；
    若 hook 改变已有规格或验证证据，在重验和重新批准完成前停止，不得继续大纲。
- 如果没有注册钩子，或 `.specify/extensions.yml` 不存在，静默跳过。

## 大纲

用户在触发消息中输入于 `$speckit-specify` 之后的文本**就是**功能描述。即使下方按字面
出现 `{ARGS}`，也应假定对话中始终可以取得该描述。除非用户提交了空命令，否则不要要求
用户重复描述。

根据该功能描述执行以下工作：

1. 为功能**生成简洁短名称**（2–4 个词）：
   - 分析功能描述并提取最有意义的关键词。
   - 创建能概括功能实质的 2–4 词短名称。
   - 尽可能使用 action-noun 格式，例如 `add-user-auth`、`fix-payment-bug`。
   - 保留技术术语和缩写，例如 OAuth2、API、JWT。
   - 名称保持简洁，但应具有足够描述性，使人一眼理解功能。
   - 示例：
     - “我想添加用户身份验证” → `user-auth`
     - “为 API 实现 OAuth2 集成” → `oauth2-api-integration`
     - “创建分析仪表板” → `analytics-dashboard`
     - “修复支付处理超时缺陷” → `fix-payment-timeout`

1a. **Bug 根因调查（Bug 修复强制，任何 `spec.md` 写入之前）**：

   - 只要请求描述的是既有行为错误、异常、回归、崩溃、错误结果或明确使用“Bug/修复”，就先执行本关卡。此时不得创建功能目录、复制模板、填写 `spec.md`、修改应用源码或提出修复方案。
   - 从用户报告、运行现象和项目证据建立事实时间线：何时/何处/如何发现、受影响环境/版本/数据、出现频率、最近已知正常状态和影响范围。未知内容必须保持“未知”；本地模式不得用 Git 历史补齐。
   - 先读取目标类/组件和相邻测试，再追踪调用方、同模块实现、配置、数据转换、并发/缓存/边界条件、日志与堆栈。运行安全可用的最小复现，记录前置状态、输入、步骤/命令、预期、实际、退出码和证据位置；不能复现时保存已有观察证据和限制。
   - 明确追踪：`触发条件 → 实际执行/数据路径 → 第一个错误状态或值 → 错误传播 → 外部症状`。分别记录根因、触发条件、促成因素、影响/爆炸半径和检测缺口；不得把相关性、最终报错点或“缺少测试”自动当成代码根因。
   - 为缺陷分配 `BUG-###`，为每个候选根因分配 `RC-###`，记录结论、支持证据、反证/替代假设、置信度和证伪方式。只有证据能解释复现与完整因果链时才把 `RC-###` 标为“已确认”。
   - 若根因未确认，仍可在完成调查后创建一份明确标为“诊断草稿”的 `spec.md`，把已知事实、候选假设、缺失证据和下一步取证写完整；但不得请求“批准规格”，不得进入 `$speckit-plan`、tasks 或实现。不得为了推进流程把假设升级为事实。
   - 把上述调查记录保留到步骤 5a/7；后续规格可以引用现有文件、符号、日志字段、堆栈帧和数据样本作为事实证据，但不能由此预设新 method/class/helper 或技术方案。

1b-0. **需求规模判定（先于成熟度评估，任何文件写入之前）**：

   按根 Skill `## 需求规模分级` 的条件判定 `XS`/`S`/`M`/`L`。

   - 逐条记录可核实证据：实际涉及文件数、涉及模块数、是否触及公开契约/数据格式/依赖、命中的 `PB-###`。存量项目必须先做只读检索确认影响面，**不得凭需求描述的字面篇幅判断**——“加个字段”可能是 `L`，“重构一下”可能是 `S`。
   - 任一条件无法用项目证据确认时取更高一档。Bug 必须在步骤 1a 确认根因后才能判定规模，因为影响面由根因决定而不是由症状决定。
   - 向用户复述：判定档位、支撑证据、该档位会跳过哪些阶段，以及“如需完整流程请要求升档”。用户可以要求升档；用户要求降档时，只能降到红线之上，红线部分照常执行。
   - `XS`/`S` 进入**精简模式**：产物只有一份 `spec.md`（变更说明），不生成独立 `plan.md`/`tasks.md`，只有一个批准关卡。`M`/`L` 进入完整模式。
   - `XS`/`S` 仍然执行步骤 1a 的 Bug 根因关卡和步骤 1b 的成熟度评估，只是共创决策点上限从 7 降为 3。

1b. **需求成熟度评估与共创对话（所有功能强制，任何文件写入之前）**：

   本关卡的目的是：需求模糊时**先和用户一起把选择讨论清楚**，而不是替用户假定后直接生成规格。
   本步骤只在对话中进行，**不得**创建功能目录、复制模板或写入任何文件。

   **b-1. 成熟度评估（内部执行，不逐项刷屏）**

   对以下十个维度分别判定 `明确` / `部分` / `缺失`，判定依据只能来自用户本轮输入、既往对话中的明确结论，以及项目内可核实的证据（代码、测试、公开契约、constitution）。不得把模型的通用假设当作“明确”：

   | 维度 | 含义 |
   |------|------|
   | D1 目标与价值 | 要解决谁的什么问题，不做会怎样 |
   | D2 用户与角色 | 有哪些使用者/权限差异 |
   | D3 范围边界 | 本次做什么、明确不做什么 |
   | D4 关键流程与交互 | 主路径的步骤与触发方式 |
   | D5 数据与状态 | 涉及的实体、关键字段、生命周期 |
   | D6 异常与边界 | 失败、并发、空态、超限如何表现 |
   | D7 成功判据 | 怎样算做完、可度量的验收标准 |
   | D8 约束与非功能 | 性能、安全、合规、时间/资源限制 |
   | D9 与既有系统的关系 | 复用哪些既有能力、哪些既有行为不得改变（存量项目强制） |
   | D10 优先级与交付节奏 | 先做什么、能否分批 |

   **b-2. 路由判定（不可由模型放宽）**

   - **直接起草**：不存在 `缺失`，`部分` 不超过 2 个，且 D1、D3、D7 均为 `明确`。此时跳过讨论循环，直接进入步骤 2，但仍必须在步骤 3a 生成精简的 `discovery.md`，把每条被采用的默认值记为“未经讨论的默认取值”。
   - **进入共创讨论**：其余全部情况。**只要 D1、D3、D7 中任意一项不是 `明确`，无论用户是否表示“你看着办”“直接写”，都必须先进入讨论循环**；用户可以在讨论中把决定权交回给你，但不能跳过把选项摆出来这一步。

   **b-3. 需求理解复述（讨论的第一条消息）**

   进入讨论循环时，先用 3–8 条要点复述你当前理解的：要解决的问题、目标用户、主路径、明确不做的部分、你已经从项目证据中确认的事实。
   紧接着用一句话说明：“以下 N 个决策点会显著改变规格，我会逐个给出选项，你确认后我才开始写 `spec.md`。”
   请用户先纠正复述中的错误，再开始第一个决策点。

   **b-4. 决策点讨论循环**

   - 内部按 `影响面 × 不确定度` 排序候选决策点，**完整模式最多 7 个、精简模式最多 3 个**，**每次严格只展示一个**，绝不提前透露后续问题。
   - 只有满足下列任一条件才能成为决策点：显著改变范围或交付量；改变用户可见行为或验收方式；影响数据模型/兼容性/迁移；影响既有行为（`PB-###`）；存在多个合理解释且代价不同。样式偏好、可安全延后到 `$speckit-plan` 的技术细节不得占用名额。
   - 每个决策点按以下格式输出：

     ```markdown
     ## 决策点 [N]/[总数]：[一句话主题]

     **问题：** [以“？”结尾的完整疑问句，脱离上下文也能读懂]

     **为什么重要：** [一句话说明它影响验收/范围/兼容性的哪一点]

     **推荐：** 选项 [X] —— [1–2 句理由，优先引用项目既有惯例或证据]

     | 选项 | 方案 | 带来什么 | 代价与风险 | 对既有行为的影响 |
     |------|------|----------|------------|------------------|
     | A | [方案 A] | [收益] | [成本/风险] | [影响的 PB-### 或“无”] |
     | B | [方案 B] | [收益] | [成本/风险] | [影响的 PB-### 或“无”] |
     | C | [方案 C，按需最多到 E] | [收益] | [成本/风险] | [影响的 PB-### 或“无”] |
     | 自定义 | 你直接描述想要的做法 | —— | —— | —— |

     你可以回复选项字母（如 `A`）、回复 `推荐` 采纳推荐项、回复 `你定` 让我代选、
     直接描述自定义方案，或回复 `跳过` 把它留到后面决定。
     ```

   - 选项必须是**互斥且都可实施**的真实方案，不得放入明显凑数项；不得把“不做这个功能”之外的合理方案隐藏起来。
   - 存量项目：任一选项会改变既有可观察行为时，必须在“对既有行为的影响”列写出具体 `PB-###` 或行为描述，并说明是否需要兼容适配层。破坏既有行为的选项不得标为推荐项。
   - Bug 修复：讨论只能覆盖修复范围、兼容取舍、验收边界和检测缺口补法。**根因不是可讨论选项**，不得用用户选择替代步骤 1a 的证据；`RC-###` 未确认时讨论循环不得产出“修复方案已定”的结论。
   - 用户回复处理：
     - `推荐` / `yes` → 采用推荐项，记为“用户采纳推荐”。
     - `你定` / `都行` → 采用推荐项，记为“由 Agent 代选”，并在规格 Assumptions 中显式标注。
     - 选项字母 → 采用该项。
     - 自定义描述 → 复述一句确认理解无误后采用；歧义时就地追问，这仍算同一个决策点。
     - `跳过` → 记为“延后决策”，采用推荐项作为当前默认值，并在规格中标注。
   - 停止条件（满足任一即结束循环）：已展示全部候选决策点；用户回复 `够了` / `开始写` / `done`；已展示 7 个决策点。
   - **硬底线**：循环结束后 D1、D3、D7 仍有 `缺失` 时，即使用户要求“直接写”，也必须在 `spec.md` 中为该项写入 `[NEEDS CLARIFICATION: ...]`，在完成报告中明确“规格尚不具备进入规划的条件”，并**不得**提出“是否批准进入规划”的问题。
   - 讨论循环期间不得输出规格草稿全文、不得写文件，也不得调用 `$speckit-plan` 或 `$speckit-tasks`。

2. **创建分支**（仅非本地模式可选，通过钩子完成）：

   本地模式必须完全跳过本步骤。如果上述执行前检查中的非 Git 本地策略之外的
   `before_specify` 钩子成功运行，它可能创建或切换 git 分支，并
   输出包含 `BRANCH_NAME` 和 `FEATURE_NUM` 的 JSON。记录这些值供参考，但分支名称
   **不决定**规格目录名称。

   如果用户显式提供了 `GIT_BRANCH_NAME`，将其原样传给钩子，使分支脚本使用该精确值
   作为分支名，绕过所有前缀/后缀生成。

3. **创建或选择规格功能目录**：

   - 新需求统一运行 `.specify/scripts/python/create_new_feature.py --json ...`，不得手工重写其目录选择逻辑。
   - 项目内模式不传 `--artifact-root`，沿用 `specs/<NNN-short-name>/` 或项目已配置的 timestamp 编号策略。
   - 外置/Obsidian 模式传入用户已确认的绝对根目录与中文需求名：

     ```text
     create_new_feature.py --json \
       --artifact-root <absolute-existing-root> \
       --folder-name <中文需求名> \
       <feature-description>
     ```

     脚本创建 `<root>/YYYY年MM月DD日-中文需求名/`；冲突时自动追加 `-02`、`-03`。只有用户明确恢复精确的既有目录时才能使用 `--allow-existing-branch`。
   - Bug 必须先完成步骤 1a，随后才允许运行创建脚本；即使只是创建空目录或复制模板，也属于被禁止的提前写入。
   - 从脚本 JSON 读取 `FEATURE_DIR`、`SPEC_FILE`、`STORAGE_MODE` 与 `ARTIFACT_ROOT`。`FEATURE_DIR` 可能位于项目之外，后续只能使用该绝对路径，不得重建为 `specs/...`。
   - 脚本负责通过活动 template 栈创建 `spec.md`，把真实路径写入 `.specify/feature.json`，把存储根、模式、活动需求和命名策略写入 `.specify/sdd-storage.json`，并在外置目录写 `.sdd-feature.json`。不得手工产生第二份规格。
   - 恢复历史需求时不创建新目录：校验用户给出的绝对目录或已保存活动指针，更新两个项目指针后，直接读取其中现有产物。多个候选必须请求用户选定，不能选最新一个。

   **重要**：

   - 每次调用 `$speckit-specify` 必须只创建一个功能。
   - 规格目录名与 git 分支名相互独立；它们可以相同，但这是用户的选择。
   - 规格目录和文件始终由本 Skill 创建，绝不由钩子创建。
   - 外置模式下不得在项目 `specs/` 生成镜像、索引副本或占位规格；项目中只保留指针配置。

3a. **落盘需求共创记录 `FEATURE_DIR/discovery.md`（强制，先于 `spec.md`）**：

   `discovery.md` 是决策的唯一权威记录；`spec.md` 只引用 `DD-###`，不重复保存选项与理由。
   即使步骤 1b 判定为“直接起草”，也必须生成精简版本，把被采用的默认值完整列出。

   ```markdown
   # 需求共创记录：[功能名称]

   **创建日期**：[DATE]
   **需求目录**：[FEATURE_DIR 绝对路径]
   **存储模式**：[project 或 external + ARTIFACT_ROOT]
   **路由判定**：[直接起草 / 共创讨论]

   ## 需求理解复述

   - [要点 1]
   - [要点 2]

   ## 成熟度评估

   | 维度 | 状态 | 判定依据 |
   |------|------|----------|
   | D1 目标与价值 | 明确/部分/缺失 | [来自用户输入或项目证据的具体依据] |
   | …（D2–D10 逐行填写） | | |

   ## 决策记录

   ### DD-001：[决策点主题]

   - **问题**：[原始问题]
   - **选项**：

   - **用户决定**：[选项 X / 自定义：… / 用户采纳推荐 / 由 Agent 代选 / 延后决策]

   ### DD-002：…

   - [默认值] —— 依据：[项目证据 / 行业标准]，可被后续 `$speckit-clarify` 推翻

   ## 延后决策

   - [DD-###]：[延后原因]、[当前采用的临时默认值]、[必须在哪个阶段之前确定]

   - [仍然缺失且已在 spec.md 标记 [NEEDS CLARIFICATION] 的条目]
   ```

   记录规则：

   - `DD-###` 编号在同一需求目录内全局唯一且只增不减。
   - 用户后续改变主意时，**追加**新的 `DD-###` 并写明“取代 DD-00X”，不得改写或删除历史决策。
   - 重新进入讨论时在 `## 决策记录` 下新增 `### 会话 YYYY-MM-DD` 分组，保留此前分组。
   - `$speckit-clarify` 与 `$speckit-plan` 产生的新决策同样追加到本文件，保持单一决策台账。
   - 外置/Obsidian 存储模式下，`discovery.md` 与其他产物一样只写入 `FEATURE_DIR`，不在项目 `specs/` 生成副本。

4. 加载已解析的活动 `spec-template` 文件，了解必需章节。

5. **如果存在**，加载 `/memory/constitution.md` 中的项目原则和治理约束。

5a. **建立存量行为基线（已有项目或 Bug 修复强制）**：
   - 读取与需求最接近的现有用户流程、公共接口文档和测试；先看目标类/组件，再看同模块和同项目的相似行为。
   - 除 Bug 根因事实证据外，这里只提取调用方可观察的行为，不把 method/class 等实现细节写入规格。Bug 可引用步骤 1a 已观察到的现有符号/路径/日志/堆栈，但只能说明“发生了什么与为什么发生”，不能规定修复方案。
   - 为每项不得改变的行为分配稳定 `PB-###`，覆盖正常路径、异常路径、边界条件、公共契约和数据兼容性。
   - 对 Bug 修复完整写入步骤 1a 的 `BUG-###`、事实时间线、受影响环境、复现证据、因果链、`RC-###` 状态/证据/置信度、促成因素、影响范围、检测缺口、未知项、期望结果以及相邻不应改变的场景。
   - 把未被用户明确要求改变的现有行为视为受保护契约；无法确定高影响行为时使用澄清问题，不能自行假定可以破坏。

6. 遵循以下执行流程：
   1. 从参数解析用户描述。
      如果为空：ERROR `No feature description provided`。
   2. 从描述中提取关键概念。
      识别：actors、actions、data、constraints。
   3. 对不清晰之处：
      - **已在 `discovery.md` 由 `DD-###` 决定的内容直接采用**，不得再标记
        `[NEEDS CLARIFICATION]`，也不得在规格中改写成与用户选择不同的方案。
      - 其余部分根据上下文和行业标准作出有依据的推断。
      - 仅在以下条件成立时使用 `[NEEDS CLARIFICATION: specific question]` 标记：
        - 该选择显著影响功能范围或用户体验。
        - 存在多个合理解释，且影响不同。
        - 不存在合理默认值。
      - **限制：总共最多 3 个 `[NEEDS CLARIFICATION]` 标记。**
      - 按影响排序澄清：scope > security/privacy > user experience > technical details。
   4. 填写 User Scenarios & Testing 章节。
      如果没有清晰用户流程：ERROR `Cannot determine user scenarios`。
   5. 生成功能需求。
      每项需求都必须可测试。对未指定细节使用合理默认值，并记录在 Assumptions 章节。
   6. 定义成功标准。
      创建可度量且技术无关的结果；同时包含定量指标（时间、性能、容量）和定性指标
      （用户满意度、任务完成情况）；每项标准无需实现细节即可验证。
   7. 如果涉及数据，识别关键实体。
   8. 返回 SUCCESS，表示规格已可进入规划。

6a. **精简模式（`XS`/`S`）的规格形态**：

   ```markdown
   **跳过的阶段**：plan、tasks（本档位不需要独立产物）

   ## 变更意图

   [做什么、为什么、对用户可见的结果是什么]

   ## 需求共创决策

   ## 受保护行为

   ## 变更前基线

   | 命令 | 预期 | 实际（执行后填写） |

   - [ ] T002 [回归验证任务]

   ## 回归验证

   - 变更后重新运行上表**同一组**基线命令，结果必须一致。
   - 每个 PB-### 的验证方式必须实际执行并记录。
   - Bug 修复还要记录：复现测试在修改前失败、修改后通过，相邻正常/边界场景仍通过。

   ## 升档触发

   - 出现以下任一情况立即停止并升档：需要改第二个模块、要动公开契约或数据格式、
     要加依赖、触到本文件未列出的 PB-###。
   ```

   精简模式**不缩减**的部分：`PB-###` 识别与前后同一基线回归、Bug 根因关卡、复用优先与 `NM-###`、破坏性变更禁止、需求成熟度评估。缩减的只是产物数量和批准关卡数量。

7. 使用模板结构将规格写入 `SPEC_FILE`。以功能描述（参数）推导的具体细节替换占位符，
   同时保留章节顺序和标题。精简模式改用步骤 6a 的变更说明结构，其余规则同样适用。

   规格必须与 `discovery.md` 保持一致：

   - 填写 `## 需求共创决策` 章节，逐条列出 `DD-###`、最终决定，以及它约束了哪些
     `FR-###`/`SC-###`/范围条目；模板缺少该章节时主动补齐。
   - Assumptions 中的每条默认值都要标注来源：`DD-###`、项目证据、行业标准三选一。
     “由 Agent 代选”和“延后决策”必须在此显式标出，让用户在批准时能一眼看到。
   - 规格正文不得出现与任一 `DD-###` 最终决定相矛盾的表述；发现矛盾时以
     `discovery.md` 的用户决定为准并修正规格，不得反向改写决策记录。

8. **规格质量验证**：写入初始规格后，按质量标准进行验证：

   a. **创建规格质量检查表**：使用以下检查表模板结构，在
      `SPECIFY_FEATURE_DIRECTORY/checklists/requirements.md` 生成文件：

      ```markdown

      **创建日期**：[DATE]
      **功能**：[链接到 spec.md]

      ## 内容质量

      - [ ] 不包含拟议实现细节（Bug 可引用既有符号/日志/堆栈作为根因事实证据）
      - [ ] 聚焦用户价值和业务需求
      - [ ] 面向非技术利益相关者编写
      - [ ] 所有必填章节均已完成

      ## 需求完整性

      - [ ] 不再保留 [NEEDS CLARIFICATION] 标记
      - [ ] 需求可测试且无歧义
      - [ ] 成功标准可度量
      - [ ] 成功标准与技术无关（无实现细节）

      - [ ] 已识别边界情况
      - [ ] 范围边界清晰
      - [ ] 已识别依赖和假设

      ## 功能就绪度

      - [ ] 所有功能需求都有清晰验收标准
      - [ ] 用户场景覆盖主要流程
      - [ ] 功能满足 Success Criteria 中定义的可度量结果
      - [ ] 规格中没有泄漏拟议实现细节；Bug 证据引用未越界成为修复方案

      ## 需求共创与决策一致性

      - [ ] `discovery.md` 已生成，并记录了十个维度的成熟度评估与判定依据
      - [ ] 每个影响范围、验收方式或兼容性的分歧点都有对应 DD-### 与最终决定
      - [ ] 规格正文没有与任一 DD-### 相矛盾的表述
      - [ ] “由 Agent 代选”“延后决策”“未经讨论的默认取值”均已在 Assumptions 中标注
      - [ ] D1 目标与价值、D3 范围边界、D7 成功判据均不为“缺失”；若仍缺失，规格已标记

      ## 存量兼容与回归

      - [ ] 所有受影响的既有行为均以 PB-### 记录并可验证

      - [ ] 公共契约、旧调用方和数据兼容要求已记录
      - [ ] Bug 修复在写规格前已完成根因调查，并以 BUG-###/RC-### 记录可复核证据
      ```

## 强制执行后钩子

**向用户报告完成之前，必须完成本章节。**

对每个实际执行的 `after_specify` hook，在执行前先对本次 `SPEC_FILE`、
`SPECIFY_FEATURE_DIRECTORY/discovery.md`、
`SPECIFY_FEATURE_DIRECTORY/checklists/requirements.md`、`.specify/feature.json`、
`.specify/task-management.json` 和存在的 plan/research/data model/contracts/quickstart/tasks
分别记录 SHA-256；执行后重新解析路径、重新计算并逐文件比较。随后无条件重新读取全部存在
的相关产物，完整重跑本阶段的存量兼容检查、Bug `BUG-###`/`RC-###` 根因关卡和整个规格质量检查表；若已有下游产物，同时重验
`NM-###`、调用方、变更前基线和回归矩阵。只有重验全部通过才能进入完成报告；变化会使此前
对该规格及下游产物的批准失效。

检查项目根目录是否存在 `.specify/extensions.yml`。

- 如果不存在，或 `hooks.after_specify` 下没有注册钩子，跳到完成报告。
- 如果存在，读取它并查找 `hooks.after_specify` 键下的条目。
- 如果 YAML 无法解析或无效，静默跳过钩子检查并继续到完成报告。
- 过滤掉显式设置 `enabled: false` 的钩子。没有 `enabled` 字段的钩子默认视为启用。
- 对每个剩余钩子，**不要**尝试解释或求值钩子的 `condition` 表达式：
  - 如果钩子没有 `condition` 字段，或其值为 null/空，则视为可执行。
  - 如果钩子定义了非空 `condition`，跳过该钩子，并将条件求值留给 HookExecutor 实现。
- 对每个可执行钩子，根据其 `optional` 标志输出以下内容：
  - **强制钩子**（`optional: false`）——对每个强制钩子都**必须输出
    `EXECUTE_COMMAND:`**：

    ```text
    ## Extension Hooks

    **Automatic Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}
    ```

    输出上述块后，**必须**实际调用钩子并等待其完成，再继续。调用方式与当前
    agent/session 中自行运行该命令的方式相同；实际调用形式可能不同于上面显示的字面
    `{command}` id，例如 skills 模式 agent 使用 `/skill:speckit-...` 或
    `$speckit-...`。只输出块并不等于运行钩子。调用前后必须完成逐 hook SHA-256 快照、
    重新读取和重验；失败时立即阻断，不得进入完成报告。
  - **可选钩子**（`optional: true`）：

    ```text
    ## Extension Hooks

    **Optional Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```

## 完成报告

向用户报告完成情况，包括：

- `SPECIFY_FEATURE_DIRECTORY`——功能目录路径。
- `SPEC_FILE`——规格文件路径。
- `DISCOVERY_FILE`——`FEATURE_DIR/discovery.md` 路径。
- `STORAGE_MODE`、`ARTIFACT_ROOT`——项目内或外置/Obsidian 模式及其根目录。
- 规模档位、判定依据和本档位跳过的阶段；并说明用户可以要求升档。
- 需求成熟度评估结论与路由判定（直接起草或共创讨论），并列出仍为“部分/缺失”的维度。
- `DD-###` 清单：每条决策的主题、最终决定，以及该决定是用户选择、用户采纳推荐、由
  Agent 代选还是延后；延后项要写明必须在哪个阶段之前确定。
- 检查表结果摘要。
- 当前任务管理后端：本地 `tasks.md` 或精确 GitLab 项目。
- 明确列出规格范围、主要需求、假设、未决问题和 `spec.md` 路径。
- 对已有项目列出 `PB-###` 受保护行为、变化/不变边界；Bug 修复还要列出复现与相邻场景。
- Bug 修复还要列出 `BUG-###`、事实时间线、因果链、每个 `RC-###` 的状态/证据/置信度、影响范围与检测缺口。
- 若存在任何未确认 `RC-###`，报告“当前仅为诊断草稿，根因尚未确认，禁止进入规划”，列出缺失证据和下一步取证，然后停止；**不得**询问用户是否批准进入规划。
- 若 D1、D3 或 D7 仍为“缺失”，报告“需求关键维度尚未确定，规格不具备进入规划的条件”，列出缺失维度和建议的下一步讨论，然后停止；**不得**询问用户是否批准进入规划。
- 只有所有适用 `RC-###` 都已确认、且 D1/D3/D7 均不缺失，才提出批准问题：
  - **完整模式（`M`/`L`）**：“请审阅当前 `spec.md` 与 `discovery.md` 中的决策记录。是否批准此版本进入澄清/规划阶段？请回复‘批准规格’，或指出需要修改的内容。”
  - **精简模式（`XS`/`S`）**：“本需求判定为 [档位]，已跳过独立 plan/tasks。请审阅当前变更说明，包括受保护行为、变更前基线和内联任务清单。是否批准直接进入实现？请回复‘批准变更说明’，或指出需要修改的内容；如需完整流程请回复‘升档’。”这是精简模式**唯一**的批准关卡，不得省略。

输出上述确认问题后**必须停止**。不得在同一轮自动调用 `$speckit-plan`，也不得把用户最初“完成整个功能”的请求视为对尚未生成规格的预批准。批准只适用于用户看到的当前 `spec.md`；规格被实质修改后必须重新确认。

**注意**：分支创建由 `before_specify` 钩子（git extension）处理。规格目录和规格文件始终
由本 core Skill 创建。

## 快速指南

- 聚焦用户需要**什么（WHAT）**以及**为什么（WHY）**。
- 避免描述如何实现（HOW）；不得包含技术栈、API 或拟议代码结构。Bug 根因证据可以引用已经存在的文件/符号/日志/堆栈作为观察事实，但不能规定解决方案或新符号。
- 面向业务利益相关者而不是开发者编写。
- 不得在规格内部创建任何检查表；那将由独立命令处理。

### 章节要求

- **必填章节**：每个功能都必须完成。
- **可选章节**：仅在与该功能相关时包含。
- 如果某章节不适用，完整删除；不要保留为 `N/A`。

### AI 生成规则

根据用户 prompt 创建规格时：

1. **项目证据优先**：已有项目先使用当前代码、测试、接口文档和相邻行为填补缺口；只有项目没有证据时，才使用行业标准和常见模式。项目传统与通用最佳实践不一致时，默认保留项目传统，除非违反宪章、安全要求或用户指令。
2. **记录假设**：在 Assumptions 章节记录合理默认值。
3. **限制澄清**：最多 3 个 `[NEEDS CLARIFICATION]` 标记，仅用于以下关键决策：
   - 显著影响功能范围或用户体验。
   - 有多个合理解释且影响不同。
   - 没有任何合理默认值。
4. **确定澄清优先级**：scope > security/privacy > user experience > technical details。
5. **像测试人员一样思考**：每项含糊需求都应无法通过“可测试且无歧义”检查项。
6. **常见澄清领域**，仅在不存在合理默认值时使用：
   - 功能范围和边界，包括/排除特定用例。
   - 用户类型和权限，如果存在多个相互冲突的解释。
   - 安全/合规需求，如果具有重大法律或财务影响。

**合理默认值示例**（不要询问这些内容）：

- 数据保留：采用该领域的行业标准做法。
- 性能目标：除非另有说明，采用标准 web/mobile app 预期。
- 错误处理：使用用户友好消息和适当 fallback。
- 身份验证方式：web app 使用标准 session-based 或 OAuth2。
- 集成模式：采用适合项目的模式，例如 web service 使用 REST/GraphQL、library 使用函数
  调用、tool 使用 CLI args 等。

### 成功标准指南

成功标准必须：

1. **可度量**：包含明确指标，例如时间、百分比、数量、速率。
2. **技术无关**：不提及框架、语言、数据库或工具。
3. **面向用户**：从用户/业务角度描述结果，而非系统内部行为。
4. **可验证**：无需了解实现细节即可测试或验证。

**良好示例**：

- “用户可在 3 分钟内完成结账。”
- “系统支持 10,000 名并发用户。”
- “95% 的搜索在 1 秒内返回结果。”
- “任务完成率提高 40%。”

**不良示例**（聚焦实现）：

- “API 响应时间低于 200ms”（过于技术化；改用“用户立即看到结果”）。
- “数据库可处理 1000 TPS”（实现细节；改用面向用户的指标）。
- “React 组件高效渲染”（特定于框架）。
- “Redis cache hit rate 高于 80%”（特定于技术）。
