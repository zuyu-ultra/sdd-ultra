# 任务：[FEATURE NAME]

**输入**：来自 `/specs/[###-feature-name]/` 的设计文档

**先决条件**：plan.md（必需）、spec.md（用户故事必需）、research.md、data-model.md、contracts/

**测试与回归**：已有项目和 Bug 修复的基线、复现、已确认 `RC-###` 与回归测试是必需关卡，不可省略。纯文档等无法自动测试的变更也必须给出可重复验证步骤。

**组织方式**：任务按用户故事分组，使每个故事都能独立实施和测试。

## 格式：`[ID] [P?] [Story] Description`

- **[P]**：可并行执行（不同文件、没有依赖）
- **[Story]**：本任务所属的用户故事，例如 US1、US2、US3
- 描述中必须包含精确文件路径

## 路径约定

- **已有项目**：只使用 plan.md 中记录的真实目录、目标符号和相邻测试，不另建平行分层
- **明确 Greenfield**：使用用户批准的 plan.md 结构；模板不预设目录或架构
- **测试路径**：沿用同模块现有测试位置、命名和 fixture 风格
- 下方所有路径都是待替换占位符，不构成创建新目录的建议

## 依赖关系与执行顺序

### 阶段依赖

- **设置（阶段 1）**：无依赖，可立即开始
- **基础能力（阶段 2）**：依赖设置完成，并阻塞所有用户故事
- **用户故事（阶段 3+）**：全部依赖基础阶段完成
  - 此后用户故事可并行推进（如果人员允许）
  - 也可按优先级 P1 → P2 → P3 顺序推进
- **完善（最终阶段）**：依赖所有期望交付的用户故事完成

### 用户故事依赖

- **用户故事 1（P1）**：基础阶段完成后可开始，不依赖其他故事
- **用户故事 2（P2）**：基础阶段完成后可开始；可以与 US1 集成，但应能独立测试
- **用户故事 3（P3）**：基础阶段完成后可开始；可以与 US1/US2 集成，但应能独立测试

### 每个用户故事内部

- Bug 修复必须先编写复现测试，并确认它在实施前因目标缺陷失败；新功能先确认既有 PB-### 基线通过
- Bug 修复在复现后必须再次核对 `RC-###`；根因被推翻时，spec/plan/tasks 批准失效并返回规格阶段
- 保护/复现测试先于对应实现
- 复用或扩展现有符号先于任何 `NM-###` 新建例外
- 核心实施先于集成
- 一个故事完成后再进入下一个优先级

### 并行机会

- 所有标有 [P] 且不共享文件、状态或回归关卡的设置任务都可并行
- 所有标有 [P] 且不会隐藏同一红线失败的基础任务都可在阶段 2 内并行
- 基础阶段完成后，所有用户故事都可并行开始（若团队容量允许）
- 一个用户故事中所有标有 [P] 的测试都可并行
- 一个故事中标有 [P] 且已在复用决策中获批的实现任务可并行
- 不同团队成员可并行处理不同用户故事

## 实施策略

### MVP 优先（仅用户故事 1）

1. 完成阶段 1：存量基线与复用确认
2. 完成阶段 2：基础能力（关键——阻塞所有故事）
3. 完成阶段 3：用户故事 1
4. **停止并验证**：独立测试用户故事 1
5. 准备就绪后部署/演示

### 增量交付

1. 完成设置 + 基础能力 → 基础就绪
2. 添加用户故事 1 → 独立测试 → 部署/演示（MVP！）
3. 添加用户故事 2 → 独立测试 → 部署/演示
4. 添加用户故事 3 → 独立测试 → 部署/演示
5. 每个故事都在不破坏先前故事的前提下增加价值

### 并行团队策略

多人协作时：

1. 团队共同完成设置和基础阶段
2. 基础阶段完成后：
   - 开发者 A：用户故事 1
   - 开发者 B：用户故事 2
   - 开发者 C：用户故事 3
3. 各故事独立完成并集成

## 说明

- [P] 任务表示文件不同且没有依赖，可并行执行
- [Story] 标签把任务映射到特定用户故事，以便追踪
- 每个用户故事都应能够独立完成和测试
- Bug 修复实施前验证复现测试确实失败，并确认 `RC-###` 仍能解释因果链；已有功能基线测试必须先通过
- 每完成一个任务或逻辑任务组就运行对应验证并记录结果；本地模式不得执行任何 Git 命令
- 可在任一检查点停止，以独立验证故事
- 避免：含糊任务、同一文件冲突，以及破坏故事独立性的跨故事依赖
- 禁止：未检索现有实现、未引用已批准的 `NM-###` 就新建 method/class/service/helper，或只验证新功能而不运行老功能回归
